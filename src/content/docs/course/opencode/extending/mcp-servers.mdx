You hit this the moment OpenCode touches `feedmill`'s database. feedmill - the course's illustrative Go feed aggregator, a CLI plus a sync server pulling RSS, Atom, and JSON feeds into one reading queue - stores that reading queue in SQLite. For this page, assume the list of feeds it pulls lives in a separate store: a `feeds` table in a local Postgres database. The repo carries only the Go code. To follow along on your own database, declare its MCP server in the same `type: "local"` shape; only the server command and its connection setting change. You ask the agent to extend a query on the dedupe path, and it writes SQL against a `feeds` table that has a `seen_at` column - except feedmill calls it `last_seen`, and there's a `source_id` foreign key the agent never mentioned because it never saw it. The schema lives in a running Postgres database, and nothing in the repo points the agent there. So it guesses from the struct definitions, gets the column names half-right, and you spend the turn pasting `\d feeds` output back at it so it can correct itself.

That pasting *is* the gap. The truth isn't in the codebase - it's in a live system the repo never mentions. OpenCode's answer is the Model Context Protocol: you declare the database as an **MCP server**, and OpenCode gives the agent a tool that queries it directly. The agent's `bash` tool could already run `psql`, if it thought to and had the connection string. An MCP tool differs in three ways: it has its own name, which the permission map can target apart from `bash`; the server can hold it to read-only queries; and the connection string stays in config, not in a command the agent types. The next time it needs the schema it runs the query itself, sees `last_seen` and `source_id` with its own eyes, and writes the migration against what's actually there.

## MCP is configuration, not code

Worth being precise about what you're adding, because MCP and plugins are easy to confuse and MCP is the lighter of the two. A **plugin** is code you write that runs inside OpenCode and can intercept its lifecycle. An **MCP server** is just a declaration in `opencode.json`, OpenCode's main config file, pointing at a process or a URL that already speaks the protocol - you write no code, you write JSON (as of September 2026; [MCP documentation](https://opencode.ai/docs/mcp-servers/)). For reaching an external system that already has (or can get) an MCP server, this is the whole job: name it, point at it, done. Save the plugin surface for when you need to *change OpenCode's behavior*, not just *give it a new system to talk to*.

MCP servers go in the `mcp` field of `opencode.json`. Each one is either `type: "local"` - OpenCode spawns a process and talks to it over stdio - or `type: "remote"` - OpenCode connects to a URL over HTTP. Pick by where the server runs, not by what it does. A local MCP process can still reach a remote database through its connection string.

## Declare a local server: the Postgres MCP

`postgres-mcp` runs on your machine, so a local server is the fit (it would be even if the database were hosted): OpenCode launches the MCP process itself and pipes to it. You describe what you want and review the edit it proposes to `opencode.json`:

> The transcript blocks in this lesson are stylized to show the flow - prompt, edit proposal, approval. Your actual OpenCode TUI (terminal user interface) may render the prefixes and prompts differently. The edit prompts appear because feedmill's `opencode.json` sets `"permission": { "edit": "ask" }`, as in [the first-change lesson](/course/opencode/getting-started/first-change/); by default the `build` agent edits without a prompt.

```text
> add an mcp server to opencode.json so you can query feedmill's local
  postgres. Use the maintained postgres-mcp server over uvx, pointed at
  the dev database in read-only mode. type local.

  | Edit  opencode.json

    {
      "$schema": "https://opencode.ai/config.json",
      "mcp": {
        "feedmill-db": {
          "type": "local",
          "command": [
            "uvx", "postgres-mcp", "--access-mode=restricted"
          ],
          "environment": {
            "DATABASE_URI": "postgresql://localhost:5432/feedmill_dev"
          },
          "enabled": true
        }
      }
    }

  Permission required
    Allow once   Allow always   Reject
```

Read the shape before you approve. `type: "local"` means the `command` array is the only required key - it's the argv OpenCode will spawn, exactly as you'd type it in a shell, split into tokens. The argv begins with `uvx` (uv's runner, which executes a Python-packaged server without installing it), so `uv` itself must be on the machine for the server to launch. The `environment` object holds env vars the spawned process needs - `postgres-mcp` reads its connection string from `DATABASE_URI`, so it goes here rather than inline in the command, keeping the connection string out of the argv that shows up in process listings. If the connection string carries a password, write `"DATABASE_URI": "{env:FEEDMILL_DB_URI}"` instead: OpenCode substitutes `{env:VAR}` anywhere in its config, so the committed file holds no credential. The remaining keys are housekeeping: `enabled` is OpenCode's on/off switch for the server at startup (leave it `true` here), `cwd` sets the working directory the process launches in, and `timeout` bounds how long OpenCode waits when fetching the server's tools. The command array is still the load-bearing part: it picks the server and, via `--access-mode=restricted`, holds it to read-only queries.

Heads-up on which Postgres server you wire in: Anthropic's old reference `@modelcontextprotocol/server-postgres` is **deprecated and archived** ([the archived repository](https://github.com/modelcontextprotocol/servers-archived) is explicit about it). Do not copy an archived server into production without reviewing its source and security history. The example above uses [`postgres-mcp`](https://github.com/crystaldba/postgres-mcp) ("Postgres MCP Pro", by Crystal DBA); pin the version you deploy, review its upstream security posture, and keep its access mode restricted to read-only.

## Watch the agent query instead of guess

Now the payoff, on the same task that bit you. One setup note first: MCP tools run without a prompt by default (as of September 2026; [tools documentation](https://opencode.ai/docs/tools/)). This run adds one rule to feedmill's `permission` block, so every tool from the `feedmill-db` server asks first:

```json title="opencode.json"
{
  "permission": {
    "edit": "ask",
    "feedmill-db_*": "ask"
  }
}
```

Ask for the migration again, and this time OpenCode reaches for the MCP tool before it writes a line of SQL:

```text
> add a column to track how many times we've seen each feed, and write
  the migration against the real feeds schema

  | feedmill-db_execute_sql  SELECT column_name, data_type FROM
    information_schema.columns WHERE table_name = 'feeds'   → approved

    id          | uuid
    source_id   | uuid
    url         | text
    last_seen   | timestamptz
    title       | text

  The table is feeds with last_seen (not seen_at) and a source_id FK.
  I'll add seen_count as an integer defaulting to 1, matching the
  timestamptz/snake_case conventions already here.

  | Edit  migrations/0007_add_seen_count.sql

  Permission required
    Allow once   Allow always   Reject
```

The agent called a tool named `feedmill-db_execute_sql` - the server's `execute_sql` tool under OpenCode's `<server>_<tool>` namespace for MCP tools, so you can always tell a tool that reaches outside the repo from a built-in like `read` or `bash` - and it ran a real query against your real database. It saw `last_seen`, not the `seen_at` it would have guessed, and it caught the `source_id` FK on its own. No pasting. The schema correction that used to cost you a turn now happens inside the agent's read step.

Notice the MCP query went through approval (`→ approved`) because of the `feedmill-db_*` rule. MCP tools are tools: OpenCode keys each one by its `<server>_<tool>` name in [the same per-tool permission map](/course/opencode/permissions/per-tool-per-agent/) as everything else, so you can `allow`, `ask`, or `deny` them like any other tool. Without a rule they run without a prompt, so a server that can *write* to your system writes unprompted until you add one. Here the write guard is `--access-mode=restricted`, which the server itself enforces; switch it to `unrestricted` and the `ask` rule is the only thing between the agent and a write. That matters most for the kind of server you'll meet next.

## Declare a remote server: url, headers, OAuth

When the MCP server itself isn't a local process - an endpoint that a hosted API, a SaaS dashboard, or a shared team service exposes - you use `type: "remote"` and point at a URL instead of spawning a command. Say feedmill's error tracking lives in a hosted service with an MCP endpoint:

```json
{
  "mcp": {
    "feedmill-errors": {
      "type": "remote",
      "url": "https://errors.example.com/mcp",
      "headers": {
        "Authorization": "Bearer {env:FEEDMILL_ERRORS_TOKEN}"
      },
      "enabled": true
    }
  }
}
```

The two keys that earn their place here are `url` - required, the endpoint OpenCode connects to - and `headers`, where you put auth that rides on every request. Resolve the token from the environment with `{env:VAR}` rather than pasting a live credential into a file you'll commit. For services that speak OAuth instead of a static token, a remote server takes an `oauth` object (or `oauth: false` to turn the flow off); OpenCode runs the authorization dance and holds the tokens for you, so you don't manage a bearer string at all. Remote entries take the same `enabled` and `timeout` housekeeping keys as local ones.

The local/remote split is the only decision that really matters: local when OpenCode should *launch* the thing and talk over stdio, remote when it should *connect* to something already running over HTTP. Everything else is the auth details for getting in the door.

## Where the declaration lives - and who it travels with

`opencode.json` layers, and MCP servers ride that layering. Put `feedmill-db` in the project's `opencode.json` at the repo root and it travels with feedmill - anyone who clones the repo gets the same database tool, no setup. Put a server in your global config at `~/.config/opencode/opencode.json` and it follows *you* across every repo - the right home for a personal tool that isn't feedmill's business. Project config merges *over* global where they overlap, and a managed/system config layers above both for org-wide policy, so a team can pin or forbid servers centrally and a project can't quietly override that (as of September 2026; [config documentation](https://opencode.ai/docs/config/)).

The practical rule: a server everyone working on feedmill should have goes in the project file and gets committed; a server that's your own habit goes in your global file and stays out of the repo. Either way you declared a system once and OpenCode handed the agent a way to reach it - the agent now has a tool for the schema. It decides when to call it, so if it still guesses, name the server in your prompt or add a line to `AGENTS.md`.

One discipline before the next declaration: MCP reach is not free context. OpenCode's own docs carry the caveat - using an MCP server adds to the context, it adds up fast when a server exposes a lot of tools, and big ones like the GitHub server can push a session past its limit (as of September 2026; [MCP documentation](https://opencode.ai/docs/mcp-servers/)). Every enabled server's tool schemas are paid for in window space - up front on clients that load schemas eagerly, at first use on clients that defer. OpenCode's docs do not say which of these it does, so read the widget's defer toggle as a behavior some clients have, not an OpenCode setting. Either way, mounting a server is a context-budget decision, not just an access decision.
