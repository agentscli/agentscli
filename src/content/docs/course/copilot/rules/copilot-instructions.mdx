Start with the bluntest instrument, because it is also the one supported everywhere: a single file, `.github/copilot-instructions.md`, scoped to the whole repo. It is **always on** - Copilot loads it on every chat request in that repo, in every role (Ask, Plan, and Agent: Copilot's built-in chat modes); as of September 2026 there is no setting to flip and no glob to match. The file shapes chat requests; nothing in the current documentation extends it to inline completions. Repository instructions are supported across the surfaces Copilot runs on - the IDEs, chat on GitHub.com, code review, and the cloud coding agent (the async Copilot that works on GitHub without your editor) - per [GitHub's custom instructions documentation](https://docs.github.com/en/copilot/reference/custom-instructions-support), as of September 2026. That breadth is what makes it the natural home for conventions that should *never* be guessed.

## Write down what Copilot kept getting wrong

The raw material for this file is not a style guide written from scratch; it is your correction history. Think back through the fixes you kept re-typing into chat. On the two packages this course follows - `orders-service`, the illustrative order-management API your squad owns, and `shared-lib`, the internal library it imports - the recurring corrections were concrete: `any` types slipping into strict TypeScript, imports missing the `.js` extension the ES modules need, floating-point math on money the codebase keeps in integer cents, and endpoints answering with ad-hoc shapes instead of JSON and standard status codes.

Create `.github/copilot-instructions.md` and write those down as plain, direct instructions. When both packages live in one repo, one file covers them both:

```markdown title=".github/copilot-instructions.md"
# Copilot Instructions

These rules apply to both `shared-lib` and `orders-service`.

## General

- TypeScript strict mode. No `any` types.
- Use ES module imports with `.js` extensions.
- Prefer named exports over default exports.

## Money

- All monetary values are integer cents.
- Never use floating point for currency math.

## API conventions

- Return JSON for all responses.
- Use standard HTTP status codes (401, 404, 422, 500).
- Authenticate via `x-api-key` header.

## Testing

- Run tests with `npm test`.
- Every bug fix needs a regression test.
- Tests must pass before merging.
```

Notice what this *is not*: not a restatement of the TypeScript handbook or generic clean-code advice. Copilot already knows that, and padding the file with the obvious only dilutes the parts that matter. The bar is the handful of things specific to *this* repo that Copilot got wrong and a teammate would have caught in review. Even this short file has a line near that edge - "Tests must pass before merging" is closer to team policy than to a correction Copilot needed. Holding that bar is the subject of the [last lesson in the chapter](/course/copilot/rules/good-rules/).

## See it work

With the file in place, give Copilot a task you would have hand-held before - say, "add an endpoint that lists pending approvals" - and read the first draft. The route should already authenticate through the `x-api-key` header and answer in JSON with a standard status code. Any money should already be integer cents. The imports should already carry `.js` extensions. You are no longer correcting style; you are reviewing logic, which is where your attention is actually worth something.

One distinction to keep honest: the file is *loaded* into context on every request, but whether the model *obeys* every line every time is not a guarantee. Instructions are guidance, not enforcement - the enforced boundaries in Copilot live in permission levels, covered in the [Permissions chapter](/course/copilot/permissions/). So when a draft still drifts, treat it as feedback on the file's wording: sharpen or add the convention and move on. Over an illustrative week or two of daily use, the file converges on the handful of rules that actually keep drafts mergeable.

:::tip[Try it]
Write three rules in `.github/copilot-instructions.md` for your repo: one about naming, one about error handling, one about test style. Open a fresh chat and ask for a small feature without mentioning the rules. Check whether the first draft follows all three; if it misses one, that rule needs sharper wording.
:::
