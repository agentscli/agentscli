OpenCode's policy boundary is configured around tools and agents. On the 1.x line, the `permission` config maps each tool (`read`, `edit`, `bash`, `task`, `skill`, `webfetch`, ...) to `allow`, `ask`, or `deny`, with pattern rules for tool input and an `external_directory` guard for paths outside the working directory. The model still sees instructions, repository files, tool output, and plugin-provided behavior, so permission rules are not a substitute for reviewing extensions or MCP servers. For untrusted work, put the whole process in a container or another host-level boundary.

Evaluate an OpenCode workflow as a small software system: use a disposable worktree, record the selected agent and model, capture tool and approval events, and run deterministic tests after the run. Check both the output and the absence of forbidden changes. OpenCode 2 (GA since September 2026) writes permissions as an ordered `permissions` array with renamed actions (`shell`, `subagent`) and allows `external_directory` by default, so confirm which line your install runs before copying a policy example from anywhere. *As of 2026-10, OpenCode 1.19.4.*
