An agent working in a real repository takes actions with very different consequences. Reading a file leaves no change behind. Editing one is reversible with `git`. Running a shell command may not be. Reading a credentials file leaks it into the conversation. A single "trust level" cannot fit all of those, so Claude Code lets you set the leash per action class and per task. Permissions are the course's **control** principle in its purest form: what guides execution, enforces boundaries, or allows intervention. Understanding an instruction is not the same as being unable to break it, and this chapter is about the second thing.

Two mechanisms do the work. A **permission mode** is a named posture that decides, in bulk, which actions stop and ask you before they run; the modes run from `default` (edits and consequential commands ask) to `bypassPermissions` (no normal prompts at all). **Allow rules** and **deny rules** are entries in your settings that move one specific action - a command pattern, a file path, a tool - to "run silently" or "refuse outright" regardless of the mode. Modes are the coarse dial; rules are the fine one.

## The running example

The examples use a small payments service: Express and TypeScript, routes in `src/index.ts`, payment code under `src/payments/`, tests under `tests/`. Each page restates the facts it needs, so you can read them in any order and you do not need a checkout to follow. What makes the service a good tour is that it presents every trust level at once:

- **Routine test runs** you would let happen freely - `npm test` a hundred times without a second thought.
- **Edits you want to see** - a mechanical rename is safe to batch, a change to the charge path is not.
- **Files the agent must never touch** - the deny-rule exercise has you create disposable `.env`, `secrets/`, and production-config placeholders, because the companion fixture intentionally ships no secrets.
- **A long batch you want to walk away from** - dozens of files and test runs, with nobody watching.

## The whole dial in one picture

Six named permission modes, tightest to loosest:

```text
 tightest ─┬─ 1  default             asks before actions that need approval
           ├─ 2  acceptEdits         auto-applies file edits, still asks for commands
           ├─ 3  plan                researches and proposes without source edits*
           ├─ 4  auto                runs hands-off with a safety classifier
           ├─ 5  dontAsk             denies calls that would otherwise prompt
           └─ 6  bypassPermissions   no normal permission prompts; isolate it
 loosest ──┘

* Plan-mode protections do not apply when the active mode is `bypassPermissions`, and in an interactive session where `bypassPermissions` appears in the mode cycle they are not enforced even while plan mode is active.
```

Read the ladder as ordering one property: how often Claude asks before acting, tight to loose. It does not order how much each mode lets Claude do without asking, and `plan` and `dontAsk` are where those two ideas come apart: both cut interruptions without granting more freedom, and `dontAsk` gets fewer prompts by denying the borderline calls instead of asking. The `plan` rung gets a fuller treatment in the planning chapter, starting with [entering plan mode to research before you change code](/course/claude-code/planning/enter/).

One fact about the starting rung before you read further: a plain `claude` launch may start in `auto`, not `default`, depending on your plan and version. That is why this course's walkthroughs launch with `claude --permission-mode default`; [the default-prompt lesson](/course/claude-code/permissions-modes/default/) states which plans and versions start where.

Allow and deny rules are a separate layer that narrows or broadens what each mode can do, and a deny rule holds whichever mode is active. The rest of the chapter takes each mode and rule layer in turn, starting from [the default prompt](/course/claude-code/permissions-modes/default/).
