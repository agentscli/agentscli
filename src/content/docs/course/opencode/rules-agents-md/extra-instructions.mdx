In `feedmill`, the course's illustrative Go feed aggregator, the `AGENTS.md` started tight - the UTC rule, the rate-limit rule - but it's filling up. Every feed source has its own shape: Atom items take their timestamp from `updated`, JSON Feed items prefer `date_published` and fall back to `date_modified`, and the linkblog fixtures carry their own decoding note. You've written all of that down once, in `docs/feed-formats.md` (assume feedmill has this file; any long conventions doc of your own works the same way), and you don't want to paste it into `AGENTS.md` - it grows with every source you add, and it would bury the two rules that actually need to be read on every turn.

So you do the thing your fingers may already know how to do. You drop a reference into `AGENTS.md`:

```markdown
## Feed parsing

See @docs/feed-formats.md for per-source conventions.
```

If you've come from Claude Code, that `@path` is muscle memory - CLAUDE.md expands an `@`-prefixed path inline, out of the box, pulling the referenced file into context automatically ([Claude Code memory documentation](https://code.claude.com/docs/en/memory), as of September 2026). So you write the rule, ask `build` (OpenCode's default coding agent) for a parser change, and watch it stall or guess on the per-source detail anyway. An illustrative exchange:

```text
build ›
> add handling for the new "linkblog" feed - its conventions are in the docs

  • Read internal/parse/atom.go   (1 file)

  I don't see a linkblog format described. AGENTS.md mentions a
  docs/feed-formats.md but I haven't read it. Want me to open it?
```

The agent had `AGENTS.md` in its context, saw the literal text `@docs/feed-formats.md`, and treated it as exactly that - literal text. It did not go open the file. **OpenCode does not automatically parse `@path` references inside `AGENTS.md`** - the docs say it plainly: "opencode doesn't automatically parse file references in AGENTS.md" ([rules documentation](https://opencode.ai/docs/rules/), as of October 2026). That `@` syntax has no special meaning here; the reference sits as a string the model can read but the tool never acts on. A habit another tool honors invisibly fails silently in OpenCode - the rule *looks* wired up, and only a stalled or wrong answer tells you it wasn't.

## Wire the file in through `instructions`, not `@`

The right place to list extra rule sources isn't `AGENTS.md` at all - it's the `instructions` field in `opencode.json`, OpenCode's config file at the project root. It takes an array of paths, and OpenCode loads every one of them into the rules layer (the instruction text OpenCode puts in the model's context on every turn) alongside `AGENTS.md` - "All instruction files are combined with your AGENTS.md files" ([rules documentation](https://opencode.ai/docs/rules/), as of October 2026) - in context from the first message of every session. A relative path resolves against the directory you start OpenCode in and each parent up to the repo root, so the entry below, added to your existing `opencode.json`, works from anywhere inside feedmill ([`instruction.ts` at v1.18.32](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/session/instruction.ts), as of October 2026):

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["docs/feed-formats.md"]
}
```

`AGENTS.md` stays the lean two-rule file it should be; the long per-source reference lives in its own doc where it's easy to read and edit; and `opencode.json` is the seam that joins them. Now re-run the same task and the detail is there before you ask. The edit below waits for approval only because this repo's `opencode.json` also sets `agent.build.permission.edit` to `ask`, the gate [the first-change lesson](/course/opencode/getting-started/first-change/) sets up; out of the box, `build`'s edits land without asking ([permissions documentation](https://opencode.ai/docs/permissions/), as of October 2026). An illustrative exchange:

```text
build ›
> add handling for the new "linkblog" feed - its conventions are in the docs

  • Read internal/feed/json.go   (1 file)

  Per docs/feed-formats.md, linkblog items follow the JSON Feed rules:
  prefer date_published, fall back to date_modified, and reject an item
  with neither. The fixture is UTF-8, and any decoding rule stays beside
  its regression fixture. I'll reuse JSONItem.PublishedAt for the UTC
  timestamp.

  ⏵ Create internal/feed/linkblog.go
  Permission required
    Allow once   Allow always   Reject
```

The conventions were already in its context this time - not because you mentioned them in the prompt, but because `instructions` puts `docs/feed-formats.md` into the rules layer the same way `AGENTS.md` gets there. No read of `docs/feed-formats.md` was needed; the file arrives exactly like the rules you wrote inline, just kept in a file of its own.

## One glob beats a growing list

The `instructions` field accepts glob patterns, not only literal paths - which matters the moment you have more than one extra source. `feedmill` is heading toward a `docs/feeds/` directory with a file per format family: `atom.md`, `json.md`, `rss.md`. Rather than naming each one and editing `opencode.json` every time you add a feed type, match them all:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["docs/feeds/*.md"]
}
```

A new `docs/feeds/microformats.md` is now picked up automatically - write the doc, no config edit. This is the same trick monorepos use to gather a `packages/*/AGENTS.md` from every sub-package in one line. The glob is the maintainable form, but it has a cost that grows with it: every match loads on every turn, so each doc you add makes every turn larger. Use it while most turns need the files and they stay short. When each file serves only some tasks, point at it in prose instead, as the last section shows.

The `instructions` field even reaches past your own repo: an entry can be a remote `https://` URL, and OpenCode fetches it into the rules layer alongside the local files - handy for a shared house style you keep in one place and point every project at. Remote fetches carry a 5-second timeout, so keep anything load-bearing local and treat the remote pull as a convenience, not a dependency ([rules documentation](https://opencode.ai/docs/rules/), as of October 2026).

## When you genuinely can't pre-list it

`instructions` is the answer when most turns need the files. Sometimes they don't - the relevant doc depends on which feed source the task touches, and pre-loading all of them on every turn would just burn context. For that case the fallback is plain prose: tell the agent *in* `AGENTS.md` to go read the file when it's relevant, in ordinary language rather than `@` syntax.

```markdown
## Feed parsing

When adding or changing a feed parser, read the matching file under
docs/feeds/ first (e.g. docs/feeds/json.md for JSON feeds).
```

That instruction the agent *can* act on, because it's a directive it understands - "read this file when X" - not an import directive it's expected to expand. It is guidance, not a load: the model usually follows it, but nothing makes it open the file. If a task skips the file and gets the detail wrong, move that file into `instructions`. The difference is the whole lesson: OpenCode won't resolve a path for you, but the model will usually follow an instruction to go read one. So either list the file in `instructions` and have it loaded for you, or write the prose and have the agent fetch it on demand. What you can't rely on is the middle thing - an `@path` that looks like both and is neither: OpenCode never loads it, and it stays text the model may or may not act on.

## Context that lives in another directory or repo: `references`

`instructions` loads files from your own project. When the context is a whole other directory or repository, such as the product docs, a shared library, or an SDK the code calls, OpenCode has a separate `references` key that gives the agent named access to it ([references documentation](https://opencode.ai/docs/references/), accessed 2026-10-25). Each entry is an alias, and it points at either a local `path` or a Git `repository`:

```jsonc title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "references": {
    "docs": {
      "path": "../product-docs",
      "description": "Use for product behavior and documentation conventions"
    },
    "effect": {
      "repository": "Effect-TS/effect",
      "branch": "main",
      "description": "Use for Effect API details"
    }
  }
}
```

How it behaves, per the docs:

- A `path` can be relative to the config file, absolute, or home-relative (`~/`). A `repository` takes a Git URL, a host/path form, or GitHub `owner/repo`; `branch` is optional and defaults to the repository's default branch. Git references refresh asynchronously, so a newly added one may take a moment to clone.
- `description` is what tells agents when to use a reference. A reference without one stays available through autocomplete but is not advertised to agents, so write a short, specific line.
- In the TUI, type `@docs` to attach the reference root or `@docs/` to search files inside it. `hidden: true` removes the alias from `@` autocomplete only; a hidden reference that has a description is still described to agents.
- Reference directories are allowed through the external-directory permission boundary, but normal tool permissions still apply, so a read-only agent does not gain edit access.
- Aliases cannot be empty or contain `/`, whitespace, backticks, or commas.

The choice between the two keys is cost. A file in `instructions` is loaded on every turn. A reference costs its resolved path and description on every turn and the files themselves only when the agent opens them, which fits large or rarely needed material.

<Aside type="caution" title="In OpenCode 2">
References exist in v2 with the same `path`, `repository`, `branch` and `description` fields. The v2 page adds details to plan around: a string shorthand counts as a local path only if it starts with `.`, `/` or `~`, so write `"./docs"` because a bare `"docs"` is read as a Git repository, and local `file:` repositories are not supported. See the [v2 references documentation](https://opencode.ai/v2/docs/references/), as of October 2026.
</Aside>

Your instruction files now span a clean `AGENTS.md` plus a set of focused docs, all in context on every turn through one config field (references, above, are the on-demand exception). Notice what it costs: every one of those files rides along on every turn, whether the turn needs it or not.
