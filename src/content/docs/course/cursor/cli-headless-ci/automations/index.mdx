[Cloud Agents and Bugbot](/course/cursor/cli-headless-ci/cloud-and-bugbot/) covers agents you start over the API and a reviewer that fires on pull requests. **Automations** generalize the second idea: an automation "runs cloud agents in the background" when a trigger fires, whether that is a clock, a pull request, a chat message, or an alert ([Automations documentation](https://cursor.com/docs/cloud-agent/automations), as of October 2026). The page does not state a beta or general-availability label for the feature.

## Creating one

You can create an automation from the Agents Window, at cursor.com/automations, with the `/automate` skill from a local agent session, or from a Cursor Marketplace template. The steps are the same: choose a trigger, write a prompt, pick optional tools, choose a repository setting (none, single, or multi-repo), then save and activate. An automation can have several triggers and runs when any of them fires.

## Triggers

| Source | Events the docs list |
|---|---|
| Schedule | Presets or a cron expression; a run may be delayed but "will not start before the indicated time" |
| GitHub, GitLab, Bitbucket Cloud | Draft opened, PR opened, PR pushed, PR merged, push to branch, comment added; GitHub adds the most (label changes, CI completed, review events), GitLab adds label changes and approvals, Bitbucket Cloud adds approvals |
| Slack | New channel message, emoji reaction, channel created (public channels only) |
| Webhook | A private endpoint you POST to; save the automation first to get the URL and API key |
| Linear | Issue created, status changed, end of cycle |
| Sentry | Issue created, issue updated, any issue event |
| PagerDuty | Incident triggered, acknowledged, resolved, any event (team admins connect the integration) |

Pull requests from forks do not run an automation, except merged-PR triggers. Bitbucket Server and Data Center are not supported.

## Tools, memory, and identity

Pull request creation is on by default for every automation. Comment on pull request posts top-level and inline comments; with approvals enabled, the agent can also approve, request changes, and dismiss reviews. Request reviewers, Send to Slack, and Read Slack channels are optional. An MCP server tool grants the agent every tool that server exposes, so the docs advise connecting only trusted servers.

**Memories** are on by default and persist across runs in a `MEMORIES.md` file; the docs warn that untrusted input can plant misleading or malicious memories, which is a reason to turn them off for an automation that reads public issues or Slack. **Computer use** is also on by default.

On team accounts, **Run as** is either you or a service account (only team admins can choose the service account; each gets its own, and archiving it stops the automation). GitHub comments and reviews post as `cursor`; pull requests open as you or as `cursor` depending on Run as.

## Cost and the control question

Usage bills as cloud agent usage, billed to you under "Me" or to the team's usage pool under a service account. The docs state that automations always use each model's maximum context window, with no toggle, so a frequent trigger on a large repository is a cost decision as much as a convenience. Because the trigger is the access-control surface here, apply the same discipline as for `@cursor` mentions: scope the repositories, keep approvals off unless you have decided a bot's approval may count toward merging, and prefer narrow triggers such as one branch or one channel.
