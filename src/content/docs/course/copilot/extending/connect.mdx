The system that knows the consumers of your team's shared library (the one other services import) is a service registry. It already has an MCP server (a tool service speaking the Model Context Protocol - a standard way for Copilot and other agents to call external systems) - most internal platforms ship one now, or it is a thin process someone on your platform team wrote. Your job is not to build the server; it is to tell Copilot the server exists and how to reach it. That is a single file.

## The file: `.vscode/mcp.json`

Workspace-level MCP servers live in **`.vscode/mcp.json`** at the root of your repo. It holds a `servers` object - one key per server, each describing how Copilot should connect:

```json
{
  "servers": {
    "service-registry": {
      "type": "http",
      "url": "https://registry.internal.example.com/mcp"
    }
  }
}
```

The keys you set depend on how the server runs:

- **`type`** - either `"stdio"` (Copilot launches the server as a local process and talks to it over standard in/out) or `"http"` (Copilot connects to a server already running at a URL). The registry is a shared internal service, so it is `http`.
- **`command`** and **`args`** - for a `stdio` server, the executable to launch and the arguments to pass it. A registry server you run locally might be `"command": "npx"` with `"args": ["-y", "@yourco/registry-mcp"]`.
- **`url`** - for an `http` server, where it lives.

Because `.vscode/mcp.json` sits in the repo, it is shareable: commit it and every teammate who opens the repo gets the same registry connection without setting anything up. The reach becomes part of the project, not a thing each person rigs by hand.

## Four ways to add one

You rarely hand-write the JSON from scratch. VS Code gives you four on-ramps (routes and commands per the [VS Code MCP documentation](https://code.visualstudio.com/docs/agent-customization/mcp-servers), verified September 2026); the first three write the same `.vscode/mcp.json`, while a dev container declares its own copy:

1. **"MCP: Add Server"** from the Command Palette - a guided flow that asks what kind of server you are adding and writes the entry for you.
2. **The Extensions view, filtered with `@mcp`** - browse servers the way you browse extensions, install one with a click.
3. **Editing `mcp.json` directly** - once you know the shape, often fastest, and the source of truth the other routes write into.
4. **`devcontainer.json`, under `customizations.vscode.mcp`** - if your repo uses a dev container, declare the server there so it is present the moment the container builds.

## Beyond this workspace

Some servers are not repo-specific - a server you personally use across every project does not belong in one repo's `.vscode/mcp.json`. For those, run **"MCP: Open User Configuration"** and add them at the user level. They follow you between workspaces instead of being committed to one. The registry stays at the workspace level, because it is *this* work's reach; a personal server lives at the user level.

Whichever level a server lives at, it is not free once connected: its tool definitions ride into the model's context on every request (unless your client defers schemas), used or not. One registry that closes a real gap earns its cost; a browse-and-install habit stacks up definitions that crowd the window before you have asked anything.
