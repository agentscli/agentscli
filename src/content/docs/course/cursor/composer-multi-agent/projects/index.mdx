The three flavors in this chapter all start with you deciding how to split the work. For a migration, a feature that touches many modules, or a small app from scratch, the splitting is itself most of the effort. **Projects** move that step to an agent. A Project is a chat with a **coordinator** agent that, in the docs' words, "takes on a larger body of work" ([Projects documentation](https://cursor.com/docs/agent/projects), as of October 2026). The coordinator plans and delegates; it does not write code itself. The agents it starts do.

Status: Cursor's changelog entry of September 10, 2026 describes Projects as "available in beta and rolling out to all users" ([changelog](https://cursor.com/changelog)). The documentation page itself carries no beta label and no numeric limits, so treat the details below as subject to change.

## What a Project does

- **Plans, then delegates.** The coordinator breaks the work down and creates agents on your behalf, running many in parallel when the slices are independent.
- **Returns work for review.** Finished work comes back to you; you can open any agent the coordinator started to follow it or talk to it directly.
- **Runs on Cloud Agents.** Projects live in the left-hand nav of the Agents Window and run on their own cloud machine, so they keep going with your laptop closed. When something has to be tested on your machine, the coordinator starts a local agent.
- **Keeps shared context.** Each Project holds a set of files that sync across every cloud and local machine its agents use. Agents write research, artifacts, codebase knowledge, and your working preferences there, so later agents do not start cold.
- **Can watch for events.** On request, the coordinator can subscribe to a Slack channel, a schedule (the docs give a daily 8:00 AM example), or your pull requests, including CI runs on a branch. It creates a subscription only when you ask for one. A **Listening** pill above the chat input shows active subscriptions and lets you remove them.

## Starting one

In the Agents Window sidebar, choose **New Project**, give it an icon and name, pick a **Workspace** (a repository available to your cloud agents; the menu offers **Connect GitHub** if none is connected), choose the **Model** the coordinator uses, and select **Create Project**. An existing top-level Cloud Agent chat can be dragged onto a Project row or added with **Add to Project**; a local chat is converted to Remote Control first.

## Who can use it

The docs list Premium and higher, Teams, Enterprise, and legacy paid plans, with Cursor 3.21.9 or later for Enterprise teams. Free, Plus, and legacy Hobby plans do not include Cloud Agents and so cannot use Projects. Projects also do not work with Privacy Mode (Legacy), because they store code in the cloud while running.

## Where it sits against the other flavors

Local fan-out and subagents leave the splitting to you; a Project makes the split a deliverable of the first step. That helps when you cannot yet write the slices down, and it costs you the precision of choosing them. Each agent the coordinator starts still has the cloud threat model from the [Cloud Agents page](/course/cursor/composer-multi-agent/cloud-agents/): repository access, secrets, and trigger authorization need their own controls, and a subscription that fires on a Slack channel is an access-control decision. Review what comes back as you would any branch.
