Codex splits trust into two dials. The **sandbox** (`-s`, the wall) sets where the agent may work - three levels, `read-only`, `workspace-write`, and `danger-full-access`, covered in [the sandbox lesson](/course/codex/approvals-sandbox/sandbox-modes/); this chapter's [model lesson](/course/codex/approvals-sandbox/two-axis/) shows why they are separate dials. The **approval policy** (`-a`, this lesson) decides which of the actions the sandbox *permits* still stop to ask you first. Picture the wall with checkpoints at the gates in it: the sandbox draws the wall, the approval policy staffs the gates. Two policies, plus one config-only form for finer control.

## A policy that used to exist, and doesn't

Older Codex material describes a third policy, `untrusted`: pause for anything not on a known-safe list of commands. It has been retired - the migration guidance in the [agent approvals and security docs](https://learn.chatgpt.com/docs/agent-approvals-security#migrate-from-the-retired-untrusted-approval-policy) says the CLI no longer supports `approval_policy = "untrusted"` and that a config still carrying it can prevent Codex from starting, so remove it wherever it lingers (checked September 2026). The known-safe list went with it. For the tight, watch-everything posture it used to provide, today's equivalents are `read-only` + `on-request` - every edit and every writing command stops - or, where fail-shut is the point, `never`.

## on-request - work inside, ask at the boundary

```text
codex -a on-request
```

The policy's logic is a boundary, not a judgment call. Under `on-request`, Codex works inside the active sandbox without asking - reads, edits, and routine commands wherever the sandbox permits them - and pauses for your `y/n` when an action needs to cross that boundary: a write outside the workspace, a network call while network access is off. That is how the [agent approvals and security docs](https://learn.chatgpt.com/docs/agent-approvals-security) define the policy, checked September 2026. With a whole policy set, the stops are the fence crossings, and you can count them from the shape of the job (the granular form below can add or remove stops per category; the precise trigger semantics live in the [config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

Take a typical in-fence job - four files read, two edited, one test run, all inside the workspace - and the count falls straight out: **zero stops**, because nothing the job does crosses the boundary. It isn't that the agent judged the edits safe; the question never came up. Hand it a job whose first move is an HTTP call - fetching a live exchange rate, say - and it stops once, at the network line, because that is a crossing.

This is the daily driver, and the right answer for most interactive work. You keep a checkpoint on every escalation - the moves that would leave the project or open a socket - and pay zero interruptions on everything inside. **You're not trusting the agent's sense of risk; you're placing a gate on a line the sandbox draws. The agent cannot redraft the boundary; it can only ask to cross it.** This is the control principle at its most literal: not guidance the agent may weigh, but a checkpoint it has to pass.

## never - run end to end, no interruptions

```text
codex -a never
```

The agent never pauses for approval. It runs the whole task start to finish, and you review the result afterward rather than the steps along the way.

This sounds reckless, and on a one-dial tool it would be - here's where the independence between the two axes earns its keep. `never` only removes the *checkpoint*. It does nothing to the *wall*. Under `workspace-write` + `never`, an in-fence job runs unattended with zero stops - and if some step had needed the network, it would simply fail, not prompt. Unattended work fails shut at the fence.

The pairing decides everything. **`-a never -s read-only`** runs autonomously with read-only reach: it can inspect the whole tree, reason, and answer in the conversation, and it cannot mutate a file - the right shape for "audit this code and summarize what you find." `-a never -s danger-full-access` removes checkpoint *and* wall at once; it has its own dedicated flag, which we'll meet - and warn you off - in the [profiles lesson](/course/codex/approvals-sandbox/profiles-for-trust/). **Zero stops is only safe when the wall makes zero stops harmless.**

## Set it persistently, not just per launch

Typing `-a` every invocation gets old. The persistent equivalent is `approval_policy` in `config.toml`. It takes `on-request`, `never`, or the granular table:

```toml
# ~/.codex/config.toml  or  .codex/config.toml
approval_policy = "on-request"
sandbox_mode   = "workspace-write"
```

That `config.toml` pairing is the same two dials, written down once instead of typed every time. You'll see in the last lesson how to give a *named* pairing - a profile you can summon with one flag.

## The granular form - when a whole policy is too coarse

Both whole policies treat every crossing the same way: `on-request` asks about all of them, `never` asks about none. When that is too coarse - you want one category of prompt to stop for you and another to flow - the third form shapes approval per category:

```toml
# illustrative shape; the config reference documents each field's values
approval_policy = { granular = { ... } }
```

The table's fields each name a prompt category: `sandbox_approval` (requests to cross the sandbox boundary), `mcp_elicitations` (confirmations raised by MCP servers), and `rules`, `skill_approval`, and `request_permissions`, which gate their own respective prompt categories as the reference defines them. The decision rule for reaching for it: only when a whole policy demonstrably interrupts you on a category you have decided to trust - not preemptively, and not before you have felt the friction. The field-by-field values and defaults live in the [config reference](https://learn.chatgpt.com/docs/config-file/config-reference); treat that page as the source of truth, checked September 2026.

One more boundary matters before profiles: outbound network access is off by default in the sandbox, so a task whose first move needs the network - a live exchange rate, a package registry, an API - fails until you open it on purpose: [why network is off, and how to widen the fence deliberately](/course/codex/approvals-sandbox/network-and-dirs/).
