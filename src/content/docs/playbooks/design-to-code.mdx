**Use this when** you have a design — a Figma frame, a mockup, a screenshot of the thing you want — and it needs to become a component in *your* codebase. The tell that you need it: you pasted an image, typed "build this," and got back roughly the right layout, a blue that isn't in your palette, and a hand-rolled toggle when your codebase has a `<Toggle>` three folders over. The agent saw the picture fine. It had no idea it was looking at *your* design system.

**What you'll have when it works:** a component that could pass review from whoever owns the design system — your named primitives reused, every color and spacing value bound to a token, zero raw hex in the diff, the states the mockup didn't show covered. Plus a durable anchor artifact, so the *second* screen costs one sentence instead of a re-explanation.

**Prerequisite:** your tokens and components must be findable in the repo — a tokens file, a `ui/` folder. If the palette lives only in a design tool nobody exported, export it first; you can't anchor to what isn't on disk.

## How this works

One fact drives every step: **an image carries looks, never bindings.** Color survives a screenshot reasonably well, but semantic tokens collapse to guesses, spacing becomes literal pixels, and anything responsive or stateful is gone — a screenshot is one frozen state. A human developer fills those gaps from memory; the agent starts every session without one. So the image is one input to the prompt, not the spec: the text you send with it decides whether the output could pass review, and the check at the end verifies the part the image never carried.

## The pass

Running example: a pricing card from a mockup, into a React + Tailwind codebase.

<Steps>

1. **Get the design in — and know what your path loses.** For a static mockup, paste or drag the image; every tool in this site's scope takes it, though a few want a specific key combo — check yours before you're fumbling mid-session. If the source is a live Figma frame, an [MCP connection](/foundations/mcp-servers/) beats a flattened export — component hierarchy, tokens, and layout as structured data instead of pixels to reverse-engineer — but only if the file is disciplined: every numeric value a bound variable, every frame on auto-layout. A file full of hand-typed numbers hands the agent the same guesses a screenshot would; people blame the integration for what is source-file hygiene. And if the target is a whole flow rather than one screen, a narrated screen recording carries what no screenshot can — every state, empty state, and error toast — which a multimodal model can turn into a phased spec before anyone writes code. *Checkpoint: the agent has the image or the structured frame, and you can say in one line what your path dropped — usually states and token names.*

2. **Anchor it in text, in the same turn as the image.** Four names, none optional: the **target** file, the **components to reuse** (with an explicit "don't create new primitives" and the states enumerated — default, hover, disabled, error), the **tokens with usage**, and the **conventions** a fresh hire would be told on day one. If a sibling component does it right, point at it — one good neighbor teaches more than a paragraph of convention:

   ```text
   > Here's the pricing card mockup [image attached]. Build it as
     src/components/PricingCard.tsx. Use the existing Card and Button
     components from src/components/ui/ — don't create new primitives.
     Match colors and spacing to the tokens in tailwind.config.ts,
     not values you read off the image. States: default, hover, and a
     highlighted "recommended" variant. Mirror the structure of
     src/components/FeatureCard.tsx.
   ```

   Skip the "components to reuse" clause and the mockup's billing toggle — annual vs. monthly, say — gets built from nothing, because the agent has no way to know one already exists three folders over. It's not a bad guess; it's the only guess available:

   ```tsx
   // unanchored — a reasonable component, invented from the pixels alone
   function BillingToggle({ annual, onChange }) {
     return (
       <button
         onClick={() => onChange(!annual)}
         style={{
           background: annual ? '#7c69f7' : '#d4d4d8',
           borderRadius: 999,
           width: 44,
           height: 24,
         }}
       >
         <span style={{ background: '#fff', borderRadius: '50%' /* ... */ }} />
       </button>
     );
   }
   ```

   ```tsx
   // anchored — "don't create new primitives" was in the prompt above
   import { Toggle } from 'src/components/ui/Toggle';
   // ...
   <Toggle checked={annual} onChange={setAnnual} aria-label="Bill annually" />
   ```

   Today the two render pixel-for-pixel identical — which is exactly why looking right can't tell you which one you got. The hand-rolled version has no focus ring, no disabled state, no reduced-motion handling, and a color that happens to match `brand-600` right now; the reused one inherited all of that the day someone else built it once and never has to again. This is the same gap step 6 checks for, one level up: unreused components, not just unbound values.

   The token line is where anchoring quietly fails even when you remember it: a tokens file gives the agent names and raw values, and if the names are even slightly vague it can't tell *when* to apply which. What works is a usage table, not a token dump — copy this shape, swap in your own values, and paste it straight into the prompt (or, better, into the file the prompt points back to once you've done this pass — step 7):

   ```text
   | Token             | Value     | Use it for                                   | Never for                              |
   |-------------------|-----------|-----------------------------------------------|-----------------------------------------|
   | `brand-600`       | `#7c69f7` | primary CTA background, active nav, badges    | body text (fails contrast on light bg) |
   | `brand-500`       | `#8f7ffa` | hover states, secondary accents, focus rings   | page backgrounds                        |
   | `surface-raised`  | `#ffffff` | cards, popovers, modals                        | page backgrounds                        |
   | `surface-sunken`  | `#f4f4f6` | inputs, wells, code blocks                     | cards                                    |
   | `text-primary`    | `#18181b` | headings, body copy                            | disabled text                           |
   | `text-muted`      | `#71717a` | captions, placeholders, disabled text          | primary CTAs                            |
   | `border-default`  | `#e4e4e7` | dividers, input borders                        | focus rings (use `brand-500`)          |
   | `p-2` / `gap-2` / `mt-2`  | `8px`  | icon-to-label gap, chip padding        | card padding                            |
   | `p-4` / `gap-4` / `mt-4`  | `16px` | card padding, form-field gaps          | page margins                            |
   | `p-6` / `gap-6` / `mt-6`  | `24px` | section gaps                           | inline gaps                             |
   | `rounded-lg`      | `8px`     | cards, buttons, inputs                         | pills, avatars                          |
   ```

   The usage column is the part a raw `tailwind.config.ts` can't carry and the agent can't infer — it's the difference between "here are eleven values" and "here's when a fresh hire would reach for each one." *Checkpoint: the prompt names all four anchors, lists states the mockup doesn't show, and the token anchor is a usage table, not a values dump.*

3. **Before any code, ask for the plan.** "Tell me exactly how you'll build this — which components, which tokens — before writing code." A misread surfaces in three lines of plan far cheaper than in three hundred lines of component:

   ```text
   > Tell me exactly how you'll build this — which components, which
     tokens — before writing code.

   ⏵ Plan
     1. New file src/components/PricingCard.tsx, structured like
        FeatureCard.tsx — a Card wrapping a header, a price row, a
        feature list, and a footer.
     2. Outer wrapper: <Card variant="raised"> from ui/.
     3. Price: text-3xl font-bold, color text-primary; period
        text-sm, color text-muted.
     4. CTA: <Button variant="primary" className="w-full">.
     5. "Recommended" badge: a <span> with a custom background
        (#7c69f7) and rounded-full — I don't see an existing badge
        component in ui/.
     6. Hover state: scale(1.02) on the whole card via a CSS
        transform.
   ```

   Two of those six lines are wrong, and the plan is where that's cheap to fix:

   ```text
   > Two corrections before you build: we do have a badge component —
     Badge, in src/components/ui/ — use variant="brand" instead of a
     custom span. And drop the hover-scale; the tokens don't define a
     hover elevation for cards. Check how FeatureCard handles hover
     instead of inventing one.

   ⏵ Read   src/components/ui/Badge.tsx
   ⏵ Read   src/components/FeatureCard.tsx
   ⏵ Plan (revised)
     5. "Recommended" badge: <Badge variant="brand">Recommended</Badge>.
     6. Hover state: FeatureCard applies hover:border-brand-500 and
        hover:shadow-md — same treatment on PricingCard.
   ```

   Left uncorrected, step 5 would have shipped a hand-rolled badge with the exact failure mode from step 2's contrast — a color that matches today and drifts on the next rebrand. Caught here, it cost one sentence. Caught after step 4, it costs a diff. If the spec itself is fuzzy rather than the plan, flip the interview first: "ask me what you need to know, one question at a time" — an agent that asks about the empty state before building is saving you a rework cycle. *Checkpoint: the plan says your component and token names back to you; anything hand-rolled gets corrected here, not after the build.*

4. **Let it build, and budget a punch list.** From a corrected plan onward it's an ordinary [agentic loop](/foundations/how-agents-work/):

   ```text
   ⏵ Read   src/components/ui/Card.tsx
   ⏵ Read   src/components/ui/Badge.tsx
   ⏵ Read   src/components/FeatureCard.tsx
   ⏵ Read   tailwind.config.ts
   ⏵ Write  src/components/PricingCard.tsx
   ⏵ Bash   npm run dev  →  compiled, no errors
   ```

   Even a corrected plan ships surface gaps — fidelity degrades with design complexity no matter how good the anchors are. Walk away from the first build with a punch list, not a verdict:

   ```text
   - [ ] focus ring on the CTA missing — the mockup never showed a
         focused state, so nothing anchored one
   - [ ] "Recommended" badge sits 2px higher than the badge slot in
         FeatureCard — right component, wrong offset
   - [ ] the annual/monthly toggle updates its own label but the price
         below it doesn't re-render
   - [ ] no disabled / "current plan" state — not in the mockup, but
         the real page needs one for the plan the user is already on
   ```

   None of these are "wrong component" or "wrong token" — the anchors already caught those. They're the ordinary residue of a mockup that only ever showed one moment in time. *Checkpoint: it compiles and renders; your punch list has items, and none of them is "wrong component."*

5. **Check the looks — rendered output and mockup actually side by side.** A glance catches gross layout mismatches; the side-by-side catches four pixels of padding, a font-weight of 500 where the design says 600 — the errors that make a page feel *almost* right in a way users notice before they can articulate. *Checkpoint: the punch list is closed at the pixel level, not the squint level.*

6. **Check the bindings — grep the diff for literals.** Looking right is not the same as being wired right: an element can render the correct color as a hardcoded hex while ignoring the token — invisible today, wrong the day the brand color changes. The check is one command, run against exactly the file the agent just wrote:

   ```bash
   $ grep -nE '#[0-9a-f]{6}|[0-9]+px' src/components/PricingCard.tsx
   9:  <Card className={cn('p-4', highlighted && 'border-[#8b7af8]')}>
   14: <h3 className="mt-[13px] font-semibold">Pro</h3>
   29: <Button className="w-full bg-[#7c69f7]">Start free trial</Button>
   ```

   Three hits, three different failures, none of them visible in the render from step 5:

   - **line 9** — `#8b7af8` isn't `brand-500` (`#8f7ffa`) or `brand-600` (`#7c69f7`) from the table in step 2; it's a lookalike shade read off the mockup, close enough that the side-by-side passed.
   - **line 14** — `13px` isn't on the spacing scale at all (the nearest steps are `mt-2` at 8px and `mt-4` at 16px) — a number typed straight off the image, not chosen from the table.
   - **line 29** — `#7c69f7` is `brand-600`'s exact value, today. This is the one that fools a reviewer, because it's pixel-identical to the correct answer right up until the brand color changes and it isn't.

   The fix is a token swap, not a rebuild:

   ```diff
   - <Card className={cn('p-4', highlighted && 'border-[#8b7af8]')}>
   + <Card className={cn('p-4', highlighted && 'border-brand-500')}>

   - <h3 className="mt-[13px] font-semibold">Pro</h3>
   + <h3 className="mt-4 font-semibold">Pro</h3>

   - <Button className="w-full bg-[#7c69f7]">Start free trial</Button>
   + <Button className="w-full bg-brand-600">Start free trial</Button>
   ```

   If the design round-trips into your design tool, spot-check a few layers in its inspector the same way: a bound fill shows as a named variable (`Fill → brand/600`); a hardcoded one shows only the swatch and hex, with no name attached. *Checkpoint: the grep returns nothing, and every layer you spot-check in the design tool resolves to a named token, not a lookalike value.* Visual fidelity decays gracefully; a hardcoded palette decays all at once.

7. **Make the anchor durable.** The first pass earned an artifact — don't let it evaporate at the end of the session. Simplest version, a section in the [rules file](/foundations/rules/):

   ```md
   ## Design system
   - Components live in `src/components/ui/` — Card, Button, Badge,
     Toggle, Input. Never hand-roll one of these; extend or compose
     the existing component instead.
   - Colors and spacing bind to the tokens in `tailwind.config.ts`,
     not raw hex or px. See the usage table in `design-system.json`.
   - New screens mirror the structure of the nearest sibling
     component (FeatureCard, PricingCard) rather than starting from
     a blank file.
   ```

   More durable version — have the agent generate the usage table itself, as data every later prompt points back to instead of prose you maintain by hand:

   ```json
   {
     "colors": {
       "brand-600": { "value": "#7c69f7", "use": "primary CTA, active nav, badges" },
       "brand-500": { "value": "#8f7ffa", "use": "hover states, focus rings" },
       "surface-raised": { "value": "#ffffff", "use": "cards, popovers, modals" },
       "text-muted": { "value": "#71717a", "use": "captions, disabled text" }
     },
     "spacing": {
       "4": { "value": "16px", "use": "card padding, form-field gaps" }
     },
     "components": {
       "Card": "src/components/ui/Card.tsx",
       "Button": "src/components/ui/Button.tsx",
       "Badge": "src/components/ui/Badge.tsx",
       "Toggle": "src/components/ui/Toggle.tsx"
     },
     "doNotCreate": ["custom badges", "custom toggles", "custom buttons"]
   }
   ```

   Either way, the second screen's prompt collapses from step 2's four anchors to one sentence: "build this like the pricing card — same rules." Or capture the working *procedure* as a [skill](/foundations/skills/), if it's the steps rather than the facts you want to hand off. *Checkpoint: the next screen's prompt is one sentence plus an image.*

</Steps>

## When not to use it

Skip the anchoring for a throwaway prototype where any styling will do — the ceremony costs more than the rework. And skip the image entirely for a tweak to an existing component: "make the CTA on `PricingCard` full-width on mobile" beats a screenshot of the same idea. The play earns its keep when the output must live in your design system, not when it must merely exist.

## Failure modes

**The mockup as the state spec.** Agents reliably build only the states the image happens to show — and a mockup shows one. *Tell: hover, disabled, and error states missing from the first pass. Fix: enumerate states in the anchor text (step 2), every time.*

**Style by adjective.** "Build a settings page, make it clean" underperforms even with perfect token and component anchoring — anchors say what to build *with*, not what good looks like:

```text
> Build a settings page for account preferences. Make it clean
  and modern.
```

Technically on-system — right tokens, right components — the result still reads generic: safe defaults, no point of view, the aesthetic equivalent of a placeholder. *Tell: output that's correct by every anchor you gave it and forgettable anyway.* Fix — replace the adjective with two or three screenshots of comparable screens from products whose *style* matches your intent, and name what to copy:

```text
> Build a settings page for account preferences, same components
  and tokens as before. Style reference: [screenshot A] and
  [screenshot B] — match their card density, the label-above-input
  pattern, and how muted the section headers are relative to body
  text.
```

The screenshots carry density, rhythm, and restraint the way the mockup carried layout — information "clean" gestures at but never actually transmits. Style travels in examples, not adjectives.

**The prototype handed over as spec.** Give the agent a vibe-coded prototype's source and its accidents — a stubbed auth check, a global mutable store — read as intent. *Tell: the prototype's shortcuts reappearing in the real implementation. Fix: screenshot the working UI, pair it with a plain-text list of what was validated versus what was a shortcut, build from those two artifacts. The prototype gets deleted.*

**Round-trip that silently can't write.** An account with read-only access to the design file can pull designs but not push back; the returning half of the workflow just never fires. *Tell: reads work, write-back "does nothing." Fix: check file permissions before debugging the integration.*

## Off the shelf

If your designs live in Figma, the anchoring plumbing already ships: Figma's official [skills for MCP](https://help.figma.com/hc/en-us/articles/39166810751895-Figma-skills-for-MCP) (as of mid-2026) come bundled with the official Figma plugin — `figma-generate-design` builds full screens from your design system, `figma-code-connect` wires components to their code counterparts. They automate steps 1–2's mechanics; the plan review in step 3 and the binding check in step 6 are still yours.

## What compounds

Each anchored pass leaves the next one cheaper: the token table, the named example component, and the captured skill accumulate into a system prompt your design system effectively wrote for itself. And a workflow inversion tends to follow — practitioners who do this daily iterate in code, where a revision costs a sentence, and sync the design file *last*, once the result is worth keeping. The agent made code the faster canvas; the design file becomes the record, not the workbench.

The same shape shows up one layer down: a design system that explains itself in a usage table needs less explaining every time, the same bet [AI-ready code](/playbooks/ai-ready-code/) makes about the rest of the codebase.
