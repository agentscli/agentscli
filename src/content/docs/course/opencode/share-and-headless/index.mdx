title: "Sharing & headless"
description: "Two of OpenCode's most distinctive moves: turn a debugging session into a public link anyone can read, then drive the same fix headless from a single command."
---

Every project has a session like this one. On `feedmill` - the course's illustrative Go feed aggregator - a single source's Atom export almost-but-not-quite parses: dates land an hour off, a handful of entries dedupe against the wrong key, and the debugging session fills up with parser code, attempted fixes, and OpenCode circling. However long you have been at it, the next instinct is the same: paste a wall of terminal output into a chat with a colleague and hope they can follow it. OpenCode gives you something better. You can hand someone the *whole session* as a URL.

That's the first half of this chapter. `/share` - a slash command typed inside the session - turns the session you're standing in, prompts, reasoning, diffs, dead ends and all, into a public link at `opncd.ai/s/<id>` that anyone can open and read in a browser, no OpenCode install required (as of September 2026; [sharing documentation](https://opencode.ai/docs/share/)). And the moment you hear "public link to my session," the next thought is the right one: *what exactly leaves the building when I do that?* So the first lesson is as much about governance as it is about the feature - the manual (the default), auto, and disabled sharing modes, what's in the payload, and how to make sure a feedmill session full of internal feed URLs doesn't become a feedmill session on the open web by accident.

The second half is where OpenCode's client/server architecture stops being trivia and starts paying rent. The same engine behind the TUI (terminal user interface) can be driven with no TUI at all: `opencode run` takes a prompt, does the work, and prints a result - and with `--format json`, prints it as a stream of JSON events a script can act on (as of September 2026; [CLI documentation](https://opencode.ai/docs/cli/)). `opencode serve` stands that engine up as a long-running HTTP server you can point automation at. Put those together and a project that already runs unattended on a cron gets an agent that can run unattended too: nightly checks, CI gates, and issues you triage straight from GitHub.

## Two surfaces, one engine

- **Share a session, and govern what leaves** - take the stuck parser session, share it for a second opinion, and lock down exactly what's allowed to leave with it - [Share a session, and govern what leaves](/course/opencode/share-and-headless/share-links/)
- **Run OpenCode headless** - drive the same parser fix as a non-interactive `opencode run` with JSON output, the way a script or a teammate's pipeline would - [Run OpenCode headless](/course/opencode/share-and-headless/headless-run/)
- **The server, CI, and GitHub** - stand up `opencode serve`, wire feedmill's checks into a CI review, and act on issues through OpenCode's GitHub integration (as of September 2026) - [The server, CI, and GitHub](/course/opencode/share-and-headless/server-and-ci/)

Hold the two halves together, because they are one architecture, and that's a practical fact rather than a framing. The share link and the headless run are the *same engine and project config* seen two ways: one session opened up for a human to read, another handed to a machine to execute (`opencode run` starts a new session unless you pass `--continue` or `--session`). If you're wiring CI this week, that symmetry is what you're depending on - the permission map, the agents, the `AGENTS.md` rules, and the plugin gates (plugins that can veto or approve the tool calls their code matches) all load for the run your pipeline triggers at 2am as they do for the session you sit in front of. They don't bind it equally, and that is the control decision here: `AGENTS.md` rules are guidance the model usually follows, while the permission map and plugin gates enforce, each only for the tools and paths it matches. Of your own config, only what is committed to the project reaches a CI runner; a permission map in your global `~/.config/opencode/opencode.json` stays on your laptop. Another difference is that nobody is there to answer an `ask` (a permission value that pauses for your approval), which the headless lesson covers. A natural sequence: share the tricky parser session for a second opinion, then turn around and run the same fix as a command. "Interactive TUI" and "automated pipeline" were never two different OpenCodes - they're one engine you can either sit in front of or point a script at. Get fluent in moving between those two and feedmill stops being a project you babysit and becomes one that mostly runs itself, with you in the loop where a human review still matters.
