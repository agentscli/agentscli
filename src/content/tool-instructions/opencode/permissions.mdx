Permissions are **per-tool per-agent**. Each primary agent (`build`, `plan`, custom) gets its own permission map:

```yaml
permission:
  read: allow
  edit: ask
  bash: ask
  glob: allow
  grep: allow
  list: allow
  task: allow
```

Switching primary agents (Tab between `build` and `plan`) effectively switches permission policies - the built-in `plan` agent denies edits except to its own plan files (`.opencode/plans/*.md`, per the v1.19.4 source) while `build` has `edit: allow`.

Wildcards `*` and `?` are supported in tool patterns (but not `**` recursive globs). Evaluation is **last-match-wins** - a common pattern is to put the catch-all `"*"` rule first and put more specific rules after it.

**Defaults are permissive:** most permissions default to `allow`; `doom_loop` (the same tool call repeated 3 times) and `external_directory` default to `ask`, and `read` denies `.env` files except `*.env.example`. Start with `opencode --auto` (also valid on `opencode run`) to auto-approve every request that is not explicitly denied; explicit `deny` rules still apply.

<Aside type="caution" title="In OpenCode 2">
OpenCode 2 still reads the map above, but its native format is one ordered `permissions` array of `{ action, resource, effect }` rules (last match wins), with `bash` renamed `shell`, `task` renamed `subagent`, and `write`/`patch` folded into `edit`. Defaults also differ: `external_directory` is allowed rather than asked (add an `ask` rule to restore the prompt), `.env` reads ask rather than deny, `doom_loop` is not an action, and the built-in `plan` agent may edit only under `~/.opencode/plan`. See [permissions](https://opencode.ai/v2/docs/permissions/) and the [migration notes](https://opencode.ai/v2/docs/migrate-v1/#permissions-and-tools), as of October 2026.
</Aside>

OpenCode itself does not ship a built-in OS-level sandbox; for stronger isolation, run the CLI inside a container (Docker, Incus, etc.) as a wrapper layer.
