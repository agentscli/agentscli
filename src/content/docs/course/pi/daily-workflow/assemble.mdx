Every piece you're about to see, you already built. This lesson doesn't teach anything new - it walks `stash`'s `.pi/` directory the way you'd walk a new teammate through it on their first day, so the nine separate lessons collapse into one mental picture.

Here's what a well-worked `stash` checkout looks like after a real week with Pi:

```text
stash/
├─ .pi/
│  ├─ APPEND_SYSTEM.md             # stash's conventions, written once
│  ├─ settings.json                 # project config - routing, tool defaults
│  ├─ damage-control-rules.yaml      # the DB/.env guardrail, in plain YAML
│  ├─ PLAN.md                       # the current unit of work, human + agent edited
│  ├─ extensions/
│  │  ├─ stash-tools.ts             # /stash command + a "re-extract URL" tool
│  │  ├─ damage-control.ts          # blocks writes to stash.db and .env
│  │  ├─ tilldone.ts                # blocks tool calls until one task is in-progress
│  │  ├─ plan-injector.ts           # keeps PLAN.md in front of the model
│  │  └─ statusline.ts              # live footer: model, context %, cost
│  ├─ prompts/
│  │  └─ triage-fetch.md            # the recurring triage pass, saved as /triage-fetch
│  ├─ skills/
│  │  └─ onboard-content-source/
│  │     └─ SKILL.md                # the "wire up a new content source" procedure
│  ├─ themes/
│  │  └─ stash-dark.json            # the one purely cosmetic file in here
│  └─ agents/
│     ├─ verifier.md                # the read-only child that checks the builder's claims
│     ├─ reextract-chain.yaml       # the batch re-extraction chain, step by step
│     └─ expertise/
│        └─ extraction-lead.md      # what the extraction lead has learned about stash
└─ (the actual stash codebase)
```

Nothing in that tree is exotic. It's markdown, YAML, and a handful of small TypeScript files, all readable in one sitting - which is itself the point Pi has been making since [module 2](/course/pi/the-core/): a harness you can read in one sitting is a harness you actually trust.

## The rules and the routing - what the agent knows before it does anything

`APPEND_SYSTEM.md` is the first thing loaded, and it's where `stash`'s facts live once and stop needing repetition: the readability extractor's known failure modes, the fetch worker's rate-limit rules, how feed dates get normalized, which tags are reserved. [Module 3](/course/pi/context/) is where this file was born; here it's just present, doing the same job it always did.

`settings.json` is where the routing from [module 4](/course/pi/models-config/) lives - cheap model for bulk re-extraction jobs, a stronger model for anything touching the search index or the fetch worker's retry logic. If a local model is in the mix for throwaway grunt work, its practical context ceiling is a known, accepted limit here, not a surprise discovered mid-task.

## The extensions - the features Pi didn't ship, built on purpose

`stash-tools.ts` is the [first extension](/course/pi/first-extension/) you wrote - the `/stash` command and the re-extract tool, still the most-used thing in the directory because it turned a repeated chore into one keystroke.

`damage-control.ts` and `tilldone.ts` are [module 6](/course/pi/rebuild-the-defaults/)'s pair: the first blocks any tool call that touches `stash.db` or `.env` outside an explicit allow-rule and aborts the turn if it's tripped; the second blocks every tool *except* its own until exactly one task is in-progress, with the task state rebuilt from session history rather than a side file that could drift out of sync. Between them, the two loudest risks of a YOLO-by-default agent - an accidental write to real data, and a run that wanders off the actual task - have answers you wrote yourself and can read in full.

`statusline.ts` is the quiet one: a footer that always shows model, context percentage, and running cost, so "how much of the window is left" and "what is this costing me" are ambient information instead of a command you have to remember to run.

## The skill and the verify loop - the no-code layer and the check that doesn't trust you

`skills/onboard-content-source/SKILL.md` is [module 7](/course/pi/skills-packages/)'s packaged procedure for wiring up a new content source into `stash` - no code, just the steps, shared with anyone who installs it the same way you did. `prompts/triage-fetch.md` and `themes/stash-dark.json` are the same module's smaller wins: a recurring triage pass you invoke as `/triage-fetch` instead of retyping, and the one file in this tree that exists purely because you have to look at the thing all day.

`agents/verifier.md` is [module 8](/course/pi/subagents/)'s reviewer - a persona file, not an extension, because the only lever it gives you *is* the file. It spawns a second, read-only Pi process against the builder's session log, has it decompose the work into falsifiable claims about data integrity, and reports back without ever taking a follow-up message from you. `agents/reextract-chain.yaml` from the same module is the other half: the batch re-extraction pipeline, written down as steps rather than re-improvised each time. It doesn't get to argue with the builder in the same thread - it reads the record and calls out what doesn't hold up, which is exactly what makes it worth having.

## The team - for when one context genuinely isn't enough

`agents/expertise/extraction-lead.md` is what's left on disk from [module 9](/course/pi/teams/)'s migration team. The personas themselves are cheap - frontmatter and a paragraph, spun up only when a job is big enough that a single agent juggling everything would be the actual bottleneck. What's worth keeping between runs is the expertise file: what the extraction lead worked out about which of `stash`'s saved sites break the new extractor, so the next lead doesn't start from nothing.

## What holds it together

None of these pieces talk to each other through anything magic - a settings file, some markdown, a few TypeScript files that hook into the same handful of lifecycle events. That's the harness. It isn't bigger than the sum of nine lessons; it's the same nine pieces, finally sitting in one directory where you can see all of them at once.
