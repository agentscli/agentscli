A skill is a folder. Inside it is one file named `SKILL.md`, and the folder name *is* the skill's identity - a skill for the audit-event convention (the team's agreed shape for recording significant events through the shared library) lives at a directory like `audit-event/`, with `audit-event/SKILL.md` inside.

## Where skills live

Copilot discovers skills from a set of known locations (locations as of September 2026; the [Agent Skills documentation](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills) covers current discovery). For a skill the whole team shares - exactly what the audit-event convention is - put it in the repository so it is committed alongside the code:

- `.github/skills/`
- `.claude/skills/`
- `.agents/skills/`

Any of the three works; Copilot reads all of them. (Those last two names are not accidental - [the cross-tool story](/course/copilot/skills/the-standard/) explains them.) For something personal that follows *you* across projects rather than living in one repo, there are user-level locations instead - `~/.copilot/skills` or `~/.agents/skills` - but a team convention belongs in the repo, where review and version control apply.

Both `shared-lib` (the course's illustrative internal library, imported by about a dozen services) and the service that consumes it need this procedure, so commit it into each repo's `.github/skills/`.

## The file

A `SKILL.md` is YAML frontmatter followed by the procedure in plain markdown. Two fields are required:

- **`name`** - lowercase, hyphen-separated, and it **must match the directory name**. Folder `audit-event/` means `name: audit-event`.
- **`description`** - a single line stating **when the skill applies** - it decides when this guidance enters Copilot's context at all. This is the load-bearing field, and the [next lesson](/course/copilot/skills/trigger/) is entirely about getting it right. Write it as a *trigger condition*, not a summary.

Here is the audit-event skill. The body is the team's convention written down as steps:

```markdown
---
name: audit-event
description: Use when recording a significant event through shared-lib's
  audit helper - e.g. approval requested or granted. Ensures every audit
  call follows the team's required shape, fields, and naming.
---

# Recording an audit event

Every significant event in our services is recorded through shared-lib's
audit helper, the same way in every repo. Follow these steps.

1. Import the audit helper from shared-lib. Do not write events directly to
   a log or the database - they must go through the helper so the schema and
   redaction rules apply.
2. Name the event in dotted form, lowercase: `<domain>.<action>`. Examples:
   `approval.requested`, `approval.granted`.
3. Pass the required fields: the actor (who triggered it), the subject (what
   the event is about, e.g. the order id), and a timestamp. Never include raw
   secrets or full payloads in the event body.
4. Record the event *after* the action it describes has succeeded, never
   before - an audit trail must reflect what actually happened.
5. If the action can fail partway, record a corresponding failure event using
   the same naming so the trail stays complete.
```

That is a complete skill. Nothing else is required.

## Bundling more than the markdown

The procedure above is pure instruction, but a skill can carry more than prose. Alongside `SKILL.md` in the same folder you can bundle **scripts, examples, or other resources** the procedure needs - a small script that validates an event payload, a reference example of a correct call, a fixture file. Copilot can reach for those bundled pieces when it applies the skill, so the skill becomes self-contained: not just *what* to do, but the tools and samples to do it well.

For the audit-event skill you might add an `examples/` file showing one correct `approval.requested` call end to end, so Copilot has a concrete pattern to match rather than reconstructing it from the steps each time. Start with the prose; add resources when you notice the agent getting the shape *almost* right.

:::tip[Try it]
Write a `SKILL.md` for a repeatable procedure in your repo - the audit-event convention above is a good model. Start a new chat and describe the situation naturally, without naming the skill. If it does not fire, revise the `description` until Copilot picks it up on its own; that one line is the whole trigger mechanism.
:::

You have written a correct skill - but writing it is not enough to make Copilot *use* it. Whether this folder ever gets pulled into a task hangs on the one line you wrote almost in passing: the `description`. [Next: the description does the triggering](/course/copilot/skills/trigger/).
