The CI review catches what arrives in a pull request. Most regressions do not arrive that politely: a dependency shifts underneath you, a flaky test becomes a real failure, drift accumulates without any single PR introducing it. The second job is a nightly pass - the wrap-up run against `main` while the team sleeps (the wrap-up being the end-of-change ritual: run the checks, then look at the tree), with a flag left for whoever is first online.

Be precise about what this job is for, because the cheap version is worthless. On the payments service - the course's running example, a small TypeScript repo - `npm test` is green today: six tests, six passing, while known defects are still in the code. The `allowAsync` race in `src/payments/rate-limiter.ts` (a read and a write across an `await` lets two callers past the limit) and a zero-balance reporting bug both slip past the suite. A nightly job that only runs the suite would sleep as soundly as the tests do. Its real job is the pass you would do by hand: run the checks, then review for what the checks cannot see, and report with evidence.

## Three parts, no framework

Do not overthink what "building a loop" means. It is three things you already have:

1. **A trigger** that fires on a schedule instead of a keystroke.
2. **The headless call** - `claude -p` with its prompt and flags, as [the headless lesson](/course/claude-code/automation/headless/) assembles it - in the fail-closed posture from [the permissions lesson](/course/claude-code/automation/permissions/): deny rules underneath, refuse-by-default mode, a tight allow list.
3. **Somewhere for the answer to land** - an issue, a channel, a log - so a verdict nobody is awake to read is not lost.

Host the trigger wherever cron already lives in your team; the agent part is identical. A scheduled GitHub workflow is the least new infrastructure after the [CI lesson](/course/claude-code/automation/ci/), so that is the version below. Two platform facts worth knowing: GitHub evaluates cron in UTC, and scheduled runs can start late when runners are busy. This is configuration to write, not a run we executed:

```yaml
name: Nightly Payments Regression
on:
  schedule:
    - cron: "0 4 * * *"
  workflow_dispatch:
jobs:
  regression:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: read
      issues: write
      id-token: write
    steps:
      - uses: actions/checkout@v7
        with:
          ref: main
      - run: npm ci
      - uses: anthropics/claude-code-action@v1
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "Run the payments wrap-up: npm test, npm run lint, npm run build. Then review the tree for regressions the checks cannot catch. If anything fails or looks wrong, open a GitHub issue titled 'Nightly regression' with the evidence. If everything passes and nothing looks wrong, do nothing."
          claude_args: >-
            --max-turns 15
            --permission-mode dontAsk
            --allowedTools "Read,Grep,Bash(npm test),Bash(npm run lint),Bash(npm run build),Bash(git status *),Bash(gh issue create *)"
```

Same action, same secret as CI. Three details differ, and each is the lesson. The `schedule` trigger with a cron line replaces `pull_request`, with `workflow_dispatch:` beside it so you can fire the job by hand before trusting the first silent night. The checkout is back because this job executes against the tree - `npm ci` installs, the suite runs - and `GH_TOKEN` hands the runner's built-in token to `gh` so the issue command can authenticate, under the `issues: write` permission. And `id-token: write` is still there: the action's default GitHub App authentication - its GitHub-side identity, separate from the API key that pays for the model - mints its token from an OIDC exchange that needs this permission, on every workflow it runs, scheduled ones included. Passing `anthropic_api_key` does not switch the App off; the documented alternative is a `github_token` input - an action input, a different thing from the `GH_TOKEN` env var that authenticates `gh` above - which this workflow does not use.

The prompt spells the wrap-up out inline - run the three checks, then review the tree for what they cannot see - rather than naming a ritual from anywhere else, so the job is one plain block of configuration. ([The skills chapter](/course/claude-code/skills/) packages this same wrap-up as a `/finish-pr` skill, if your repo already carries it.) Note what it demands on failure: an issue with evidence, not an apology in a log nobody reads.

`Grep` is in the allow list for exactly that review half, and it is worth seeing why it has to be. On a Linux runner the search tools are not in the default set - Claude otherwise searches through the Bash tool, which this list deliberately does not grant - and naming `Grep` in `--allowedTools` is the documented move that restores the search tools. Control shapes capability here: with the list as written, the run can find every caller of a changed path and nothing else; drop `Grep` and the "review the tree" half quietly becomes "read what was already named".

## Fail closed, cap it, keep it read-mostly, make it loud

An interactive run that goes wrong is caught in seconds, because you are watching it. A nightly loop that goes wrong runs to completion alone, and you find out in the morning. The guardrails are the reason the job is allowed to exist at all. Four of them carry the weight:

- **Fail closed on permissions.** This is the [fail-closed permission posture](/course/claude-code/automation/permissions/) doing its job: `dontAsk` plus the tight allow list lets the run execute the checks and open an issue, and refuses everything else. There is no human to wave through the thing you did not anticipate, and the deny rules hold underneath in every mode. The allow list keeps its inner quotes for the same reason as the pull-request workflow: to a shell-style splitter, `npm run build` is three words.
- **Cap the run.** `--max-turns` is a hard ceiling on iterations; `timeout-minutes` is the outer wall that kills the job even if the process misbehaves. A confused run left alone can burn the whole night otherwise.
- **Keep it read-mostly.** The job observes and reports. It does not push fixes, so morning-you reviews the flag with the repo exactly as it was. The more an unattended loop is allowed to mutate, the larger the radius when it is wrong. Let the night job find the problem; let a human, awake, approve the fix.
- **Make the result loud.** A regression found and never surfaced is worse than no loop, because it breeds false confidence. The prompt opens an issue on failure and stays silent on success, so silence means clean and a fresh issue means look now - but silence is only meaningful once the run is known to have happened, and a workflow that never started looks exactly like a clean pass until someone opens the Actions tab. That is what the `workflow_dispatch:` trigger is for: run the job once by hand the day you write it, before you trust the first silent night. Pick whatever channel your team actually watches.

The pattern underneath all four: an unattended loop should be narrow, capped, walled, and loud. Narrow in what it can touch, capped in how long it runs, walled off from anything a mistake would make expensive, and loud enough that its findings cannot be missed. Get those right and a nightly job is a teammate on the graveyard shift. Get them wrong and it is a robot with your credentials and all night to use them.

## The fifth guardrail: done is a claim

All four quietly assume the run can tell success from failure at all. With nobody watching, the agent's "done" is a claim, and what turns the claim into a fact is the checks the run must actually get past. Play all three endings. Shipping on the claim outsources the checks to production. Build and types are the lint-green trap: both pass, nothing exercised the behavior. The full stack retries the reds and flags the seam break honestly - a failure that lives between two services, invisible to unit tests that pass against their own mocks of the other side - and even then, the misread ticket ships green, the one defect no wired check catches. That is the standing division of labor this course ends on: the machine verifies what can be wired; the morning review verifies what cannot.

## Where the course goes last

Step back at what you have assembled. The review pass you used to run by hand now runs in two places without you: on every trusted, same-repository pull request the moment it opens, and every night against `main` before anyone is awake. Fork pull requests need the separate secret-safe design from the CI lesson. Both jobs use the same headless call the chapter started with ([`claude -p`, a prompt, and flags](/course/claude-code/automation/headless/)), wrapped in the same three-layer posture ([deny rules, `dontAsk`, a tight allow list](/course/claude-code/automation/permissions/)), fired by a trigger instead of a keystroke.

Automation turned out not to be a new capability. It is the old one with the human removed, and the watching you used to do yourself is now done by the machinery this course already built: the [permission modes](/course/claude-code/permissions-modes/) that decide when the agent must ask, the [allow rules](/course/claude-code/permissions-modes/rules/) that pre-grant exactly the boring commands, the [deny rules](/course/claude-code/permissions-modes/deny/) that hold in every mode, and the [hooks](/course/claude-code/extending/hooks-gate/) that enforce conditions no prompt could.

And with whole jobs running unattended, this course has reached its widest zoom.
