The last of the chapter's three flavors leaves your machine entirely. **Cloud Agents** (formerly **Background Agents**) are full agents that run in **isolated cloud VMs** rather than locally: they clone your repo to a fresh branch, work, push results back, and you review the branch like any other. One gate to know up front - they require a paid Cursor plan (the docs' troubleshooting: "You need to be on a paid Cursor plan"), so on the free tier this course assumes you can follow this page's ideas but not start one (the pricing docs list Cloud Agents from the Premium tier up, as of October 2026). Those VMs are Cursor-hosted by default; the Cloud Agents API can also route runs to worker pools you host yourself, when execution needs to happen on hardware you control ([API endpoints](https://cursor.com/docs/cloud-agent/api/endpoints)). Everything on this page is as of September 2026 ([Cloud Agents documentation](https://cursor.com/docs/cloud-agent)).

The environment they run in is reproducible from a checked-in file, `.cursor/environment.json`, configured one of three ways:

- **Agent-led setup** - the agent installs what it needs interactively, and you snapshot the result.
- **A saved snapshot** - a captured machine image the agent boots from.
- **A Dockerfile** - a fully declared, reproducible build environment.

The snapshot path looks like this - illustrative, not the full schema:

```json
{
  "snapshot": "POPULATED_FROM_SETTINGS",
  "install": "npm install",
  "start": "npm run dev",
  "terminals": [
    { "name": "tests", "command": "npm test -- --watch" }
  ]
}
```

The `snapshot`, `install`, `start`, and `terminals` fields are the real field names (terminal entries take a `name` and `command` (an optional `description` is also defined); `ports` is a separate top-level array). One thing the example deliberately leaves out: the Dockerfile mode doesn't use a bare `snapshot` field - it uses a `build` object (`{dockerfile, context}`) instead. The canonical schema is published at [cursor.com/schemas/environment.schema.json](https://cursor.com/schemas/environment.schema.json); consult it before treating any one example as the whole story.

Because a Cloud Agent doesn't live in your editor, it's reachable from wherever your work already happens. Before anyone can start one from a repository, a Cursor account admin has to connect source control for the account - GitHub, GitLab, Bitbucket, or Azure DevOps. After that:

- **Cursor Desktop** - pick Cloud from the dropdown under the chat box where you prompt the agent.
- **Cursor web** (cursor.com/agents) - drive it from any device.
- **Cursor for iOS** - start and manage agents from the iOS app (on Android, cursor.com/agents installs as an app).
- **Slack** - `@cursor` in a channel.
- **GitHub** - comment `@cursor` on a PR or issue.
- **Bitbucket** - comment `@cursor` on a PR.
- **Linear** - `@cursor` on an issue.
- **Microsoft Teams** - `@Cursor` with a prompt, via the [Teams integration](https://cursor.com/docs/integrations/microsoft-teams).
- **The API** - spawn and manage agents programmatically, for webhooks and CI.

Cloud Agents can also build interactive **canvases**, which the Cursor changelog of October 16, 2026 announces as something they "can now build" ([changelog](https://cursor.com/changelog)); the entry gives no plan or status label.

### Where the tools run: managed VMs, My Machines, Team Pools

"Cursor-hosted" is the default, not the only runtime. The Self-Hosted Machines docs keep one thing fixed: "The agent loop still runs in Cursor's cloud," and only the tool calls run on hardware you control ([choosing a runtime](https://cursor.com/docs/cloud-agent/self-hosted/choose-runtime), as of October 2026).

| | Managed Cloud Agents | My Machines | Team Pools |
|---|---|---|---|
| Tool calls run on | A Cursor-managed isolated VM | The machine of the user who started the worker | Your worker fleet |
| Intended for | Default, no hardware to run | Personal or small-scale workflows | Org-wide fleets with central ownership; the docs name "Enterprise teams" |
| You operate | Nothing | The machine: it must stay online while sessions run, plus cleanup | Capacity, resets, updates, incident response |
| Dashboard secrets | Applied | None | Team and user secrets through Secret sync |

All three support Privacy Mode. My Machines use the machine's own credentials. Cursor-hosted VMs are x86_64, so arm64 work needs a self-hosted worker on arm64 hardware. The CLI starts workers with `agent worker`; recent releases added a macOS worker option, `agent worker --computer-use start`, that lets Cloud Agents use that Mac's signed-in desktop ([CLI changelog](https://cursor.com/docs/cli/changelog), release 2026.08.26). This is the answer to "the code may not leave our hardware" questions, with the limit that the loop and prompts still go through Cursor's cloud.

### Delegating a whole project

If you want an agent to split a large job across several Cloud Agents for you, see [Projects](/course/cursor/composer-multi-agent/projects/).

For `budgetcli` - the course's illustrative personal-finance API - a Cloud Agent is the right tool when the work shouldn't tie up your local machine and doesn't need your eyes mid-flight: "open a PR upgrading the test dependencies and confirm the suite still passes" is a job you fire from Slack on the way out and review as a PR when it's green. Your laptop never enters the loop, but cloud access, repository credentials, network access, secrets, and trigger authorization still need their own controls.

That puts the chapter's three flavors on the table - this chapter's fleet fan-out, delegated subagents, and these remote Cloud Agents. What is left is the part that actually saves you time in a working week: telling them apart fast enough to reach for the right one before you have spent the compute on the wrong one - a cost-and-control call in the course's terms: what each flavor spends, and what boundary its machine puts around the run. One more option sits on top of them: an agent that does the splitting for you. [Next: Projects](/course/cursor/composer-multi-agent/projects/).
