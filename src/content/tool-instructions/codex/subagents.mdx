Codex ships **three built-in subagents**:
- **`default`** - general-purpose fallback
- **`worker`** - execution-focused (implementation/fixes)
- **`explorer`** - read-heavy codebase exploration

**Custom subagents** are standalone TOML files at `~/.codex/agents/<name>.toml` (user) or `.codex/agents/<name>.toml` (project). One agent per file; the `name` field is authoritative.

**TOML schema - required:** `name`, `description`, `developer_instructions`. **Optional:** `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, and `skills.config` (disables individual skills). Unset optionals inherit from the parent. `sandbox_mode` and `mcp_servers` placed in an agent file do not override the parent session.

```toml
name = "reviewer"
description = "Reviews a diff for bugs, performance, and security issues."
developer_instructions = "..."
model = "gpt-6.1-sol"
```

**Invocation:** natural-language dispatch from the parent (e.g. *"Have the reviewer agent look at the diff…"*). Codex only spawns when explicitly asked. The `/subagents` CLI command **inspects** and switches between active agent threads - it does not spawn them.

**Tool restriction:** Codex's documented TOML schema has no explicit `tools` / `allowed_tools` allowlist field. A subagent inherits the parent turn's sandbox, approval settings and MCP servers; an agent file cannot replace them. It can only switch off capabilities by setting feature keys such as `features.shell_tool`, `features.apps` or `features.memories` to `false`. Instructions asking an agent not to edit do not create a read-only sandbox. (Related open issue: [#15250](https://github.com/openai/codex/issues/15250).)

The OpenAI **Agents SDK** is the heavier orchestration layer - for complex multi-agent workflows beyond what the CLI exposes directly.
