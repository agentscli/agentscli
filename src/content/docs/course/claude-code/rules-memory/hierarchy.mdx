A `CLAUDE.md` is a file of standing instructions that Claude Code loads into the model's context. Its **scope** is the location it lives at, and the location decides who receives its rules: every project on your machine, everyone who clones this repo, only you in this repo, or only sessions that work inside one subtree. Different rules want different audiences, and one file cannot serve them all.

Three rules from a small TypeScript payments service (the example this course returns to; each page restates the facts it needs) make the problem concrete:

- *processPayment's idempotency key is optional - never assume a caller sends one.* This is project truth: `processPayment` in `src/payments/processor.ts` declares `idempotencyKey?: string`, so a caller can omit it and get no duplicate check. Every teammate's agent should carry this line.
- *Show me your plan before you edit.* This is your habit, in every repo you open. Your teammates run looser, and your preference has no business in their sessions.
- *The ledger is in-memory; balances reset on restart.* True of `src/payments/ledger.ts`, and relevant only when the agent is working inside `src/payments/`.

The scope ladder gives each of those three the right audience.

## The scopes, broadest to narrowest

`CLAUDE.md` files live at several locations, each with a different reach. In the order Claude loads them, widest scope first, most specific last:

```text
Managed policy   OS-specific managed path                              (org-wide, IT-deployed)
User             ~/.claude/CLAUDE.md                                  (you, every project)
Project          ./CLAUDE.md  or  ./.claude/CLAUDE.md                 (team, this repo)
Local            ./CLAUDE.local.md                                    (you, this repo only - gitignore it)
Subdirectory     ./src/payments/CLAUDE.md                             (team, this subtree - proposal; loads on demand)
```

One line there names a file that does not exist: the example repo has no `src/payments/CLAUDE.md`. This lesson proposes one to show the mechanism, and because the in-memory-ledger note is a genuine candidate for it, though at this repo's size the project file covers the ground. The other four scopes:

- **Managed policy**: org-wide instructions your platform team deploys to an OS-specific path. You cannot override or exclude them, which is why a company standard survives a local file. Most engineers never write one.
- **User** (`~/.claude/CLAUDE.md`): personal habits across *all* projects. The show-me-your-plan preference goes here. It follows you between repos and never lands in a teammate's checkout.
- **Project** (`./CLAUDE.md` or `./.claude/CLAUDE.md`): the team-shared truth for *this* repo, committed to git. The payments service's file lives here, and the optional-key rule joins it. Most rules land here.
- **Local** (`./CLAUDE.local.md`): your personal notes for this one project, kept out of git: your scratch workflow, your local overrides. Add it to `.gitignore` so it never ships to a teammate.

The exact managed-policy paths differ by operating system, so take them from the [memory reference](https://code.claude.com/docs/en/memory) rather than hardcoding one platform's.

## They stack - they don't fight

The part people get wrong: these files **do not override each other.** Claude Code loads the user file plus every `CLAUDE.md` and `CLAUDE.local.md` it finds from the filesystem root down to your working directory, and **concatenates them all** into one combined context. Launched at the payments repo root, that means the user file and the project file. Launched from a nested directory, each ancestor's file joins too. None cancels another.

Order matters without being winner-takes-all. Content is laid out broadest to most specific; the file closest to where you launched is read *last*. Within a single directory, `CLAUDE.local.md` is appended after `CLAUDE.md`, so your personal notes are the final word at that level.

The practical upshot: a more specific instruction sits later in context and tends to win attention when two rules brush the same topic. Flatly contradictory guidance is another matter. Claude may simply pick one. That is not a feature to lean on; it is a reason to keep layers consistent and to prune contradictions whenever you audit the files.

The layers you will actually use stack like this, each concatenated onto the last, none replacing the one above it:

```text
 ~/.claude/CLAUDE.md               your rules            (loaded first, every project)
        |
        |   +  concatenated, not overridden
        v
 repo-root/CLAUDE.md               the team's rules      (added next, this repo)
        |
        |   +  concatenated, not overridden
        v
 repo-root/src/payments/CLAUDE.md  subdirectory rules    (proposed; read last, on demand)

 result: one combined context = user + project + subdirectory, all present at once
```

Subdirectory files differ in *when* they load. Files at or above your working directory load in full at launch. A file below it, such as the proposed `src/payments/CLAUDE.md`, is pulled in on demand, when Claude reads a file in that subtree. That is what makes per-subsystem rules cheap: the payments rules cost nothing until the agent goes there.

Rules can also live as topic files under `.claude/rules/`, one markdown file per topic. A file with `paths:` frontmatter, a list of glob patterns, loads only when Claude works with matching files. A file without it loads at launch, like `.claude/CLAUDE.md`. Both are ways to keep the root file short while a subsystem's rules stay close to the code they describe. The [memory reference](https://code.claude.com/docs/en/memory) documents both forms.

The Claude Code answer, in prose: working on a file at the root, the user-wide file and the project root file load. Working on a file in `packages/api/`, the nested file joins them, and the path-scoped rule joins when its `paths:` pattern matches the file being read. Working in `packages/web/`, only the two always-on files load. Nothing replaces the root file.

:::note[Check what actually loaded]
Two commands, two jobs. `/memory` lists memory-file locations across user and project scopes, including files that do not exist yet, and opens any of them in your editor, creating a selected file first if needed. It also toggles auto memory and opens the auto-memory folder. What loaded *this session* is the job of `/context`: it breaks the window into categories, so look for your file under **Memory files**. If a rule is not being followed, the first check is whether its file appears there at all.
:::
