## Billing depends on the plan and routing mode

Cursor's billing is not one universal flat rate. What a request costs can depend on your plan, the selected model, the routing mode, and whether the work lands in included or additional usage. Treat the [live Cursor pricing page](https://cursor.com/pricing) and your usage dashboard as the source of truth; pricing details are exactly the kind of thing that shifts between releases (as of September 2026).

- **Included usage** - plan-specific usage that covers some requests or model work.
- **Additional usage** - on-demand or token-based charges that may apply after included usage, depending on plan and configuration.
- **Routing choices** - Auto or another routing mode changes which model is selected and how usage is accounted for. Do not infer billing from the model name alone.

The safe decision pattern is short. Use Auto for routine work while its current routing and price fit. Use a specific model, or a bigger context, when the quality or context is worth the current cost. And check the usage dashboard before repeating an expensive pattern - a choice that looks fine once is what a day of turns multiplies.

That's the lever. You're choosing a model and a routing and billing posture together, and the skill is spending deliberately - the judgment you already apply to how much latitude a task deserves, aimed at the meter instead.

:::note[Teams add a Cursor Token Rate]
On **Teams** plans there's an extra layer: a **Cursor Token Rate** applied on top of the model's underlying cost, with Cursor's own models exempt ([Teams pricing](https://cursor.com/docs/account/teams/pricing), as of September 2026). So the math on a team plan isn't just "the model's per-token price" - it's that price plus the team rate. If you're on an individual plan this won't bite; if you're on a team plan, it's why the same model can cost you more than the price a teammate on a personal account is quoted.
:::

## Composer

One name on the roster isn't a third-party vendor's - **Composer** is Cursor's own model, built by Anysphere. Cursor 2.0 introduced it as their first agentic coding model, "a frontier model that is 4x faster than similarly intelligent models" in the changelog's words ([2.0 changelog](https://cursor.com/changelog/2-0)), and the line has iterated since - the Composer in today's model picker is newer than the 2.0-era original. It's an *agentic coding model*: trained for the edit-test-fix loop the agent runs, not a general chat model bolted into an editor.

The reason Composer matters here is that it is Cursor's own agentic model, not that it guarantees one billing treatment. Its availability, included usage, and pricing vary by plan and release. Choose it when its behavior fits the task, then confirm the current cost in Cursor's pricing and usage surfaces.

## Max Mode and context size

**Max Mode** is the control older tutorials treat as universal, and it no longer is (as of September 2026). Cursor's docs now title the feature "Max Mode on legacy plans": it is available **only on legacy request-based plans**, where it extends a model's context window beyond the default limit and is billed at **the model's API rate plus 20%** ([Max Mode docs](https://cursor.com/docs/context/max-mode)). Two details from that page: the setting persists once toggled on, and models that require Max Mode enable it automatically when you select them. On current usage-based plans there is no Max toggle at all - context size rides the model you pick rather than this legacy switch (the Max Mode page covers legacy plans only, as of September 2026).

Either way, the judgment is the same. The right time to reach for more context is a genuine whole-codebase reasoning task where the limiting factor is *how much the model can see at once* - a cross-cutting refactor, a bug whose cause and effect are in different corners of `budgetcli` (the course's illustrative personal-finance API). The wrong time is everyday work, where you may be paying for context you do not use.

### The friction: model and plan behavior changes

Here's the sharp edge: model availability, context limits, and billing treatment change across releases and plans, and some models interact with context controls differently than others. Check the model picker and pricing details for the current release instead of assuming a model-selection rule from an older tutorial.

The operator takeaway doesn't depend on which models are on the list this month: **selecting a stronger or longer-context model can change the request's cost.** That's not a reason to avoid those models - it's a reason to reach for them *on purpose*, on the turns where their reasoning earns the current bill, rather than leaving one pinned out of habit.

One workflow turns this billing structure into a deliberate move: buy the strong model's reasoning exactly once, by planning with it and building with a cheaper model. [Next: plan with one model, build with another](/course/cursor/models/mixing-models/).
