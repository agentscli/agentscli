## Gate: Hooks

MCP (Model Context Protocol) *widened* what the agent can reach. Skills and commands *packaged* what you keep repeating. None of them is a guarantee - they all depend, in the end, on the model choosing to do the right thing. There's one move in `budgetcli` (the course's illustrative TypeScript personal-finance API) where "the model usually chooses right" is precisely the wrong assurance: **Cursor must never write to your real ledger database.** It can read it, reason about it, generate a migration for you to review - but the live table where your actual balances are counted is off-limits to automated writes. An accidental `UPDATE` there isn't a bug you catch in review; it's wrong numbers in your own money.

That line - guidance versus enforcement - is the *control* principle in this course's sense: control is what guides execution and enforces boundaries. Rules, skills, and commands guide; nothing fails when the model ignores them. You could put the ledger rule in `AGENTS.md` and ask nicely, and it would usually hold. But for the one thing that must never slip, you want a wall that fires *every single time*, no matter what the model decided. That's a **Hook** - introduced in **Cursor 1.7** to let you "observe, control, and extend the agent loop using custom scripts": a subprocess Cursor runs at a fixed point in its lifecycle. The agent doesn't choose to invoke it and can't reason around it - though the hook still has to be configured and loaded, and a broken one can fail in ways you have to design for (more on that below).

### Where hooks live and the schema

Hooks are configured in a `hooks.json`, at the user or project scope:

- **User** - `~/.cursor/hooks.json`
- **Project** - `<repo>/.cursor/hooks.json`
- **Enterprise / Team** - distributed by the platform rather than a file you edit: managed system paths on Enterprise installs, dashboard-synced on Team plans. Precedence runs Enterprise, then Team, then Project, then User.

The schema names an event and the command(s) it triggers:

```json title=".cursor/hooks.json"
{
  "version": 1,
  "hooks": {
    "beforeShellExecution": [
      {
        "command": "./.cursor/hooks/protect-ledger.sh",
        "matcher": ".*",
        "failClosed": true
      }
    ]
  }
}
```

Two fields of that definition matter for a policy hook. `matcher` is a regex filter on what triggers the script - for `beforeShellExecution` it matches the command string, and `.*` takes everything. `failClosed` decides what a *broken* hook does; the default is the opposite of what you'd want for a wall, and we'll get there after the contract.

### The event surface - pick the right moment

Hooks attach to lifecycle **events**, and picking the right event is most of the design. Cursor names the moments of the loop directly - a shell command about to run, a file about to be read, an MCP tool about to be called - where some other agents give you one generic pre-tool hook to match against. The full list (about 21 events as of September 2026 - [hooks documentation](https://cursor.com/docs/hooks)) changes between releases, so re-check it before you depend on a specific name. The following is a representative grouping rather than a promise of an exact count:

- **Agent** - `sessionStart`, `sessionEnd`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `subagentStart`, `subagentStop`, `beforeShellExecution`, `afterShellExecution`, `beforeMCPExecution`, `afterMCPExecution`, `beforeReadFile`, `afterFileEdit`, `beforeSubmitPrompt`, `preCompact`, `stop`, `afterAgentResponse`, `afterAgentThought`.
- **Tab** (inline completion) - `beforeTabFileRead`, `afterTabFileEdit`.
- **App lifecycle** - `workspaceOpen`.

That `beforeShellExecution`, `beforeReadFile`, `beforeMCPExecution` trio is the policy-enforcement workhorse - command allowlisting, secret scanning, gating MCP tool calls. The read and MCP moments get dedicated event names in Cursor; Claude Code reaches the same effect through its generic `PreToolUse` hook with a `Read` or `mcp__<server>__<tool>` matcher rather than a named event. For our ledger wall we want **`beforeShellExecution`**: it fires *before* a shell command runs, the only moment you can stop a write from ever happening.

### Wire it up: stdin in, JSON out

Cursor hands the hook a JSON payload on **stdin** describing the call, and reads the verdict from the hook's **stdout** (JSON) and its **exit code**:

```bash title=".cursor/hooks/protect-ledger.sh"
#!/bin/bash
set -euo pipefail
trap 'exit 2' ERR

# Field paths are illustrative - verify them against the installed hooks schema.
input=$(cat)
command=$(jq -er '.command' <<<"$input")

# Refuse any write that targets the live ledger database.
if echo "$command" | grep -Eqi 'ledger_prod|UPDATE .*ledger|INSERT .*ledger|DELETE .*ledger'; then
  echo '{"permission":"deny","agent_message":"Writes to the production ledger are blocked. Generate a migration for review instead.","user_message":"Blocked a write to ledger_prod."}'
  exit 0
fi

echo '{"permission":"allow"}'
exit 0
```

There are two ways to signal a verdict, and the script above uses the explicit one. The **`permission`** field - `"allow"`, `"deny"`, or `"ask"` - is the nuanced channel: emit it as JSON on stdout with exit `0`, optionally with `agent_message` (fed back to the model as the reason) and `user_message` (shown to you). The blunt channel is the **exit code**: Cursor documents exit `2` as a block, equivalent to `"permission": "deny"`. Every other failure - a crash, a timeout, a non-zero exit that isn't `2` - **fails open by default**: Cursor logs the failure and lets the action through, which is exactly the wrong default for a security hook. The documented remedy is `failClosed: true` on the hook definition, so those failures block too; the script above adds a belt to that suspenders by trapping its own errors into an explicit exit `2`. Between the two, a broken hook denies rather than allows. Test the deny, malformed-input, timeout, and allowed-command paths before relying on it.

### Watch the wall hold

An illustrative exchange - Cursor finishes some balance-reconciliation work and reaches for the database (the rendering below is simplified, not a byte-accurate capture of Cursor's chat):

```text
> apply the corrected balances to the ledger

  Run  psql budgetcli -c "UPDATE ledger_prod SET balance_cents=… "

  ⊘ Blocked by hook (protect-ledger.sh):
    Writes to the production ledger are blocked. Generate a migration
    for review instead.

  Understood - I can't write the live ledger directly. I'll emit the
  corrections as a reviewed migration instead.

  Edit  migrations/0007_reconcile_balances.sql
    -- review and apply this yourself
```

Watch what the agent did with the rejection. It didn't get stuck - it read the `agent_message` the hook fed back, understood *why*, and rerouted to the safe path: a migration you apply by hand. The gate didn't just stop a bad action; it steered Cursor toward the right one. And once it's configured and loaded, it fires the same way with auto-run (the run-mode setting from the permissions chapter) set to run everything, in a [headless CLI](/course/cursor/cli-headless-ci/) run, at 2am with nobody watching. That's the property no rule or skill gives you, and that allow/deny lists give you only for named command patterns: the hook can run arbitrary logic at any wired moment of the loop, and **the model doesn't get a say in whether it runs.**

## What you've built - and which surface to reach for

`budgetcli` can now reach past its own files, carry its procedures across sessions, and refuse the one move that must never happen:

- **MCP servers** gave the agent *reach* - it queries the real Postgres schema and the live exchange-rate API instead of guessing, declared once in `mcp.json` (project to share, user to keep personal), added by hand or in one click from the Cursor Marketplace / cursor.directory.
- **Agent Skills** packaged the CSV-import *procedure* into a `SKILL.md` the agent loads when the work matches - and, in a format Cursor's docs point to as the open standard (agentskills.io), a teammate's `.claude/skills/` version works unchanged.
- **Custom slash commands** turned the prompts you kept retyping into `/commit-msg`-style templates - the natural home, alongside Skills, for prompts you used to stash in the now-deprecated Notepads.
- **Hooks** put a deterministic *wall* around the production ledger that fires whether or not the model cooperates.

All four surfaces - plus the rules layers from the earlier chapter - live in a small, regular file layout: `.cursor/` in the repo for what the team shares, `~/.cursor/` for what follows you, and a couple of layers that are settings rather than files at all. Here it is at a glance, file by file:

The distinction worth carrying out of this chapter is the one that's easy to blur: **reach when the agent can't see the system; structure when you're repeating yourself; a gate when the model's judgment isn't a guarantee you can accept.** Reach for the wrong one and you'll fight it - a hook where you wanted a skill, a command where you needed a subagent. Reach for the right one and the agent stops re-deriving, re-asking, and occasionally getting the unforgivable thing wrong.

The property that sets a configured hook apart from the other three surfaces - it runs at the lifecycle event without asking the model whether to invoke it - matters most in the setting this chapter kept gesturing at: the agent running at 2am with nobody watching.
