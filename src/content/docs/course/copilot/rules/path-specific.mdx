title: Path-specific rules with applyTo
description: "The files other teams import need stricter rules than the rest of the code. Scope those rules to a path with applyTo, layered on top of the repo-wide file."
---

A repo-wide file has one blind spot: it treats every file in the repo the same. That is fine until part of the repo deserves stricter handling than the rest. A shared library is the standing example - in this course's illustrative scenario, `shared-lib`, the internal library whose validation, auth, and audit helpers a dozen services import. A sloppy change there ripples outward in a way a change to a private utility never would. You want the helpers held to a tighter standard than the repo's tests and scripts, and "be more careful *here*" is exactly what a single repo-wide file cannot express.

Path-specific instructions are the tool for that - `*.instructions.md` files under `.github/instructions/`, each scoped by an `applyTo` glob. You write a rule that attaches only to files matching the glob, and Copilot pulls it in *in addition to* the repo-wide file when the files it is editing match.

## How they're structured

Path-specific rules live as `*.instructions.md` files under `.github/instructions/` - Copilot looks there recursively, so you can organize in subfolders. Each file carries frontmatter, and the load-bearing field is **`applyTo`**:

```markdown
---
applyTo: "shared-lib/src/**/*.ts"
description: "Stricter rules for the shared helpers consumed by 12 services"
---

These files are imported by ~12 downstream services. Treat every change as
potentially breaking.

- Never change an exported function's signature or return type without flagging
  it explicitly in your summary - it is a breaking change for consumers.
- Add new behavior behind new exports; prefer additive changes over edits to
  existing exports.
- Every audit event goes through the existing event-type union - extend the
  union, don't pass free-form strings.
- Validation rules are pure and side-effect free. Keep them that way.
```

The fields:

- **`applyTo`** *(required)* - a glob, relative to the workspace root, deciding which files this rule attaches to. `"shared-lib/src/**/*.ts"` scopes it to the library's source tree, recursively, and nothing else - not its tests, not the service next to it in the same repo ([glob examples](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions) as of September 2026).
- **`name`** and **`description`** *(optional)* - labels describing what the rule is for.

Copilot reads `.github/instructions/` by default. An older setting, `chat.instructionsFilesLocations`, could point it at additional locations, but it is **deprecated and only used by the Local agent** (the pre-Agent-Host agent that still loads these settings; per the [custom instructions documentation](https://code.visualstudio.com/docs/agent-customization/custom-instructions), as of September 2026). If you configured instruction locations with it, move those files into supported locations rather than relying on the setting.

## They combine, they don't replace

The part to internalize: when the files Copilot is editing match your glob, the path-specific rule **combines with** the repo-wide file (your `copilot-instructions.md`, `AGENTS.md`, or `CLAUDE.md`) - it does not override it. [GitHub's repository instructions page](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions) states it directly, as of September 2026: when the path matches and a repository-wide file also exists, "the instructions from both files are used." For a file under `shared-lib/src/`, Copilot holds both in context: the repo's general conventions *and* the stricter helper rules. The repo-wide file says "this is how we write code here"; the path-specific file adds "and in this directory, treat every change as potentially breaking." Layered, not either-or.

That is why the mechanism maps so cleanly onto a shared library: general conventions apply everywhere, and the high-consequence source directory gets an extra ring of rules wrapped around exactly the paths that ripple. The judgment is the same one behind [matching latitude to risk](/course/copilot/modes/switching/) - expressed in files instead of chat roles.

:::caution[IDE and cloud agent only - not GitHub.com chat]
Path-specific `*.instructions.md` files are honored in **IDE chat** (VS Code, JetBrains, and other editors) and by the **cloud coding agent**, but **not** in chat on GitHub.com, per [GitHub's customization support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support) as of September 2026. A teammate asking Copilot a question in the browser gets the repo-wide file but not your `applyTo`-scoped rules. Do not put a rule you depend on *only* in a path-specific file if it also needs to hold for browser chat; keep anything universal in the repo-wide file.
:::

## A practical split

For a service-plus-library setup, a clean division falls out:

- Your service repo - a repo-wide file is usually enough; your squad owns it and the stakes are even across it.
- The shared library - a repo-wide file for general conventions, **plus** a path-specific file over the library's source directory encoding the "many consumers, treat every change as breaking" discipline.

Rules can also arrive from more than one machine- and org-level source at once. When layers disagree, something has to win. [How rules layer - personal, repo, organization](/course/copilot/rules/hierarchy/).
