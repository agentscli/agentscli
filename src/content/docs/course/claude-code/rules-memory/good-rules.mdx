A `CLAUDE.md` is a markdown file of instructions that Claude Code loads into the model's context at the start of every session. One line of it is a rule. The file is not a free notepad: each line spends context before you have typed a word of the actual task, and the spend repeats on every session, including the ones that never touch the rule's subject. So a line has to do more than be true. It has to change what the agent does, on work that recurs, in a way the agent could not get anywhere else.

Here is the rules body of the example repo's `CLAUDE.md`, complete. The repo is a small TypeScript payments service (the example this course returns to; each page restates the facts it needs):

```markdown
## Money handling

- Use integer cents for all money calculations. Never use floating point for currency.
- Store amounts as `number` representing cents (e.g. $19.99 = 1999).

## Testing

- Run tests with `npm test`.
- Never commit without passing tests.
- Every bug fix must include a regression test.

## Code style

- TypeScript strict mode. No `any` types.
- Use ES module imports with `.js` extensions.
- Prefer named exports over default exports.
```

Eight rules in three sections. Three of its entries are among the best rules you could write for this repo, and a fourth is missing. Working these cases gives you the whole discipline.

## The economics of a rule

A rule is context you pay for **once** instead of re-establishing **every session**. That is the entire trade. Before the cents rule was written down, somebody re-taught it every session, or nobody did and the code floated. After the rule exists, the fact walks into every session on its own and the re-teaching stops.

The trade only works while the entry is *true, durable, and not otherwise available*. Pad the file and you invert it: context rent every session for lines that do not change behavior. The canonical guidance is to keep each file [under about 200 lines](https://code.claude.com/docs/en/memory). Longer files cost more and get followed less, because signal drowns in noise.

## What belongs

The rules that pull their weight share a shape: specific, verifiable, and particular to this project. They are things the agent cannot infer and would otherwise get wrong. The repo's own file supplies the worked examples.

**The domain fact that bites.** "Use integer cents for all money calculations. Never use floating point for currency." The agent has no way to know this, and the failure mode is money computed wrong. The pair of lines does the job: the first states the constraint, the second, with its `$19.99 = 1999`, makes it actionable. This is the most valuable entry in the file, and the repo's own `src/payments/processor.ts` shows why it is needed: it computes the fee as `req.amount * 0.029` in floating point, against this rule.

**The rule with a future.** "Every bug fix must include a regression test." Concrete enough to check in a diff, durable enough to outlast any one fix, and it binds work that has not happened yet. Every bug fixed in this repo from now on answers to this line.

**The convention the toolchain does not force.** "Use ES module imports with `.js` extensions." The repo's `tsconfig.json` uses bundler resolution, and `tsx` and Vitest tolerate extensionless imports, so nothing in the build complains when an agent writes `from "./processor"`. Plain Node ESM does complain. A team choice that is invisible until it bites is exactly what the file is for.

**The rule the file lacks.** `processPayment` in `src/payments/processor.ts` declares its key as `idempotencyKey?: string`, optional. A caller that omits it gets no duplicate check at all, because `checkIdempotency` never runs, so new code that assumes a key always arrives is wrong. The candidate line: *processPayment's idempotency key is optional - never assume a caller sends one.* Durable, project-specific, checkable in review.

The tell across all four: each is concrete enough that you could *check* whether the agent followed it. Testability separates the rules that change behavior from the rules that spend tokens.

## What doesn't

The entries to keep out are the ones that feel responsible and change nothing:

- **Generic best-practice filler.** "Write clean code." "Handle errors properly." The model already aims for these; the words compete with your real rules for attention.
- **Anything the code already states.** The framework is Express, the language is TypeScript, the directories are what they are. Claude reads those. Transcribing the repo into the file describing the repo buys nothing. Catching a line like that is the job of the [audit you run on every `/init` suggestion (the command that drafts this file for you)](/course/claude-code/rules-memory/init/).
- **One-off state.** "We're implementing the idempotency plan this week." True now, noise next month, misleading the month after, and a session about the rate limiter carries it anyway. This week's state belongs in the prompt or in a plan file on disk, not in a file every future session loads.

The honest test for any candidate line: *would I tell a new teammate this, can't they find it in the repo themselves, and will it still be true in three months?* Yes to all three, it is a rule. Vague, obvious, or temporary, leave it out. You are curating, not dumping.

:::note[Specific beats polite]
"Use 2-space indentation" outperforms "format code nicely" because `CLAUDE.md` is context the agent *interprets*, not configuration it is *forced* to obey. The more concrete and unambiguous the instruction, the more reliably it lands. Write rules you could grade.
:::

One more look at the file's best line before moving on. The cents rule is in context every session, and `processor.ts` still computes the fee as `req.amount * 0.029` in floating point and adds it to the amount, with a green test asserting a total of `2056.971`. A rule that earns its slot informs; it does not compel. Enforcement is a separate mechanism, and [the hooks chapter](/course/claude-code/extending/) builds it.

## Apply the test

Suppose a teammate on another service opens a `CLAUDE.md` pull request with four candidate lines. You own the review: keep or cut each one, on the tests from this lesson, before reading the verdicts:

- "Handle errors properly and write clean code."
- "Timestamps are stored as UTC milliseconds; convert to local time only in the UI."
- "We are moving the invoice endpoints to the v2 router this month."
- "Never call `lockInvoice()` from a request handler - it holds a database lock; only the nightly job may take it."

The verdicts, explained. Cut the first: filler the model already aims for, competing with your real rules for attention. Keep the second: concrete, durable, invisible in the code, and checkable in any diff that touches a date. Cut the third: true now, noise next month. This month's migration belongs in a plan file or the prompt, not a file every future session loads. Keep the fourth: a project-specific landmine no reader could infer, and one wrong call would teach expensively.

The rules you keep still need homes. The optional-key rule is team truth. A rule like "Show me your plan before you edit" is yours alone. A rule saying the ledger in `src/payments/ledger.ts` keeps its balances in memory would matter only inside `src/payments/`.
